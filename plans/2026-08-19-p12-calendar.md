# P12 - Training calendar

## Problem summary

`docs/ROADMAP.md`'s P12 entry: a monthly calendar with per-day training intensity
derived from volume, day cells showing which plan day was used, tapping a day opens
the session, month navigation, and a compact year view. This is the first Post-MVP
phase after P11 (statistics and charts, merged to `main` at `3c312b2`, PR #16).
`features/calendar/` is currently an empty skeleton (six `.gitkeep` subfolders); no
`CalendarRepository` exists yet and none is named in `docs/ARCHITECTURE.md` section
8.3 today (it jumps from `StatisticsRepository` straight to a "follow the same shape"
list that does not actually include `calendar`).

## Acceptance criteria (from ROADMAP.md, verbatim scope)

- `local_date` grouping is correct across timezone changes.
- A month with no workouts renders cleanly (a real empty state, not a blank grid).
- Navigating twelve months is smooth (no jank, no unbounded query growth).
- Commit message target: `feat: add training calendar with monthly workout overview`.

## Decisions confirmed with the user (Step 0)

1. **Dev client / build verification**: keep deferring. Continue using
   typecheck/lint/tests/`npx expo export --platform ios` as the build-verification
   proxy, same as every phase since P4 - no Xcode/Android Studio installed locally,
   EAS cloud build stays available but unused this phase. Re-offer next phase per
   `feedback_build_verification` memory.
2. **Repository shape**: build a dedicated `CalendarRepository` (read model, feature:
   `calendar`) that queries `v_session_summary`/`v_working_set` directly - the same
   "flat DTOs, no service, read the shared view" pattern P10's `HomeDashboardRepository`
   and P11's `StatisticsRepository` already established. This resolves the
   `calendar --> workout-logging` edge `docs/ARCHITECTURE.md` section 9.1 currently
   draws as real to "never built", the same way `docs/adr/0019-home-dashboard-read-model.md`
   resolved the equivalent `statistics --> workout-logging` edge. A new ADR
   (`0020-calendar-read-model.md`) records this in Step 10.
3. **Heatmap/intensity reuse**: Calendar owns its own month/year intensity query and
   quantile-binning logic in `features/calendar/domain/` - a deliberate, small
   duplication of `features/statistics/domain/yearlyHeatmapBinning.ts`'s math, the
   same precedent `features/statistics/domain/localDate.ts` already set by duplicating
   `home`'s calendar-math primitives rather than creating a cross-feature dependency.
   Rendering reuses the existing feature-agnostic `components/charts/HeatmapView` (a
   shared component, not a feature-to-feature dependency) for the compact year view.
   No new `calendar --> statistics` edge.
4. **Calendar grid UI**: custom-built `CalendarMonth`/`CalendarDayCell`/`CalendarLegend`
   against the existing design system (`theme/tokens.ts`), matching P11's precedent of
   custom-building `StackedBarChartView`/`HeatmapView` rather than adding a library. No
   new npm dependency.
5. **Multi-session-per-day tap behavior**: a day cell with exactly one completed
   session navigates directly to `history/[sessionId]` (existing P9 screen). A day with
   more than one session (rare - same-day AM/PM training) opens a small in-app picker
   sheet listing that day's sessions, reusing existing list-row components; no new
   screen for the common single-session case.

## Task shape and scale

Single application (GymTracker, React Native/Expo), one feature, multi-layer within
one repo (domain calculators -> repository -> hooks -> components -> screens ->
navigation). No schema migration needed - reuses `v_session_summary`/`v_working_set`
and the existing `ix_session_local_date` index verbatim. Steps run once, scaled by
layer per "One feature spanning layers": domain+repository-interface first (fixes the
contract), then the SQLite implementation, then the UI layer once the real repository
exists and can be wired through `services/container.ts`.

Platform: React Native / Expo (cross-platform mobile), already established - no new
platform-detection questions needed.

## Affected layers

- Domain (pure calculators): `features/calendar/domain/`
- Repository (SQLite read model): `features/calendar/repository/`
- Hooks: `features/calendar/hooks/`
- Components: `features/calendar/components/`
- Screens: `features/calendar/screens/`
- Navigation: `app/profile/calendar.tsx` (new thin wrapper), `navigation/routes.ts`,
  `app/(modals)/` (new day-session-picker modal only if the multi-session case needs a
  route rather than an in-place sheet - decided during implementation, kept in-place
  as a sheet first per decision 5's "no new screen" framing)
- `services/container.ts`: add `calendarRepository`
- `features/profile/screens/ProfileScreen.tsx`: add a "Training calendar" row
  (mirrors the existing Records/History/Measurements row precedent)
- No auth, no new API, no schema change, no new npm dependency.

## Step-by-step implementation sequence

1. **backend-agent-sonnet** (sequential, first): define the `CalendarRepository`
   interface + DTOs (`features/calendar/repository/CalendarRepository.ts`) and the
   pure domain calculators (`features/calendar/domain/`): month-grid generation
   (weeks/day cells for an arbitrary month, gap-filled per `dateRangeBuckets.ts`'s
   "generate gap-free buckets, never load-all-then-bucket-in-JS from a second
   hand-written SQL date expression" precedent), quantile-based day/month intensity
   binning (a calendar-scoped transcription of `yearlyHeatmapBinning.ts`'s approach,
   per decision 3), and `localDate.ts`-style calendar-math primitives (again a
   deliberate duplication, not an import, matching `statistics`' own precedent for the
   same reason: `calendar` may not depend on `statistics` or `home`). This step fixes
   the contract every later step builds against.
2. **database-agent** (sequential, after step 1): implement
   `features/calendar/repository/SqliteCalendarRepository.ts` against the fixed
   interface - `monthOverview(year, month)` (per-day: `localDate`, session id(s),
   `plan_day_name_snapshot`, `total_volume_kg`) and `yearOverview(year)` (per-day
   trained/not-trained + volume, feeding the compact year view's binning), both
   reading `v_session_summary`/`v_working_set` directly, fully parameterized,
   `deleted_at IS NULL`/`status = 'completed'` filtered (inherited for free from the
   views). Wire `calendarRepository` into `services/container.ts`.
3. **frontend-agent** (sequential, after step 2 - needs the real repository wired
   into the container): `useCalendarMonth`/`useCalendarYear` hooks under
   `['calendar', year, month]` (the query key `docs/ARCHITECTURE.md` section 12.1
   already reserved), `CalendarMonth`/`CalendarDayCell`/`CalendarLegend` components,
   the day-session picker (in-place sheet, decision 5), `CalendarScreen`
   (month/year toggle, month navigation, empty-state for a workout-free month per the
   roadmap's own acceptance line), `app/profile/calendar.tsx` thin wrapper, the
   `routes.profile.calendar()` helper in `navigation/routes.ts` (the route path
   `profile/calendar` is already named in `docs/ARCHITECTURE.md`'s route graph), and
   the new "Training calendar" `ListRow` on `ProfileScreen.tsx`. Also adds
   `['calendar',*]` to `features/*/hooks/invalidation.ts`'s `finishWorkout`
   invalidation set (already named as a target in section 12.1's table, not yet wired
   since the feature didn't exist).
4. **test-agent** (after step 3, or per-layer as each lands): property-based tests
   for the domain calculators (fast-check, per the project's domain-testing
   convention), a repository integration test against `NodeSqlExecutor` (real
   `schema.sql`, not mocks), component/screen RNTL tests for
   `CalendarMonth`/`CalendarDayCell`/`CalendarScreen` including the empty-month and
   multi-session-day cases, and a benchmark case added to
   `__tests__/database/benchmarks.perf.test.ts` for `yearOverview` over the existing
   75,000-set fixture (feeds the "navigating twelve months is smooth" acceptance line).
5. **security-agent-sonnet** (Step 9, conditional - triggered: new SQL queries):
   routine check of the two new repository methods for parameterization and
   `deleted_at`/`status` filtering consistency with the existing `v_session_summary`
   view.
6. **accessibility-agent** (Step 9e, conditional - triggered: new screens/components):
   check the day-cell grid (labeled, operable via screen reader and keyboard-adjacent
   interaction), the month/year toggle, and the multi-session picker sheet - the
   codebase's own recurring `SwipeableRow`-collapse finding class does not apply here
   (no `SwipeableRow` usage planned), but chart-accessibility findings from P11
   (missing textual fallback for Skia-rendered content) are directly relevant to the
   year view's reused `HeatmapView`.
7. **docs-agent** (Step 10): update `CLAUDE.md` (P12 status paragraph, matching the
   P10/P11 write-up depth), `docs/ARCHITECTURE.md` (add the real `CalendarRepository`
   entry to section 8.3, update section 9.1's dependency graph note the same way
   ADR-0019's resolution was documented, confirm section 10's route graph - already
   correct), write `docs/adr/0020-calendar-read-model.md`, update `docs/ROADMAP.md`
   to mark P12 complete, regenerate `docs/architecture-snapshot.md`'s P12 status
   paragraph.
8. **git-commit-agent** (Step 11): split by layer - domain+repository-interface,
   SQLite repository + container wiring, UI layer (hooks/components/screens/
   navigation/ProfileScreen row), tests, docs. Plan file rides with the first commit.

## API contracts (repository interface, fixed before parallelization)

```
CalendarRepository (read model, feature: calendar)

monthOverview(year: number, month: number): Promise<CalendarDayDto[]>
  // one entry per day-with-activity in the month; days with no session are absent,
  // the UI layer gap-fills the empty days the same way dateRangeBuckets.ts does
  // CalendarDayDto: { localDate, sessionIds: string[], planDayNames: string[], totalVolumeKg }

yearOverview(year: number): Promise<CalendarYearDayDto[]>
  // one entry per trained day in the year, feeds the compact year view's binning
  // CalendarYearDayDto: { localDate, totalVolumeKg }
```

## Error handling strategy

Read-only repository, no mutation surface - no new failure mode beyond an empty
result set (handled as the roadmap's own "clean empty state" acceptance line) and the
existing SQLite-unavailable path already handled by `ExpoSqlExecutor`/the app boot
gate. No new error taxonomy needed.

## Edge cases to address

- A month with zero completed sessions - empty grid state (explicit roadmap
  acceptance line).
- A day with more than one completed session - picker sheet (decision 5).
- Month navigation across a year boundary (December -> January, January -> December).
- DST/timezone boundary days - `local_date` is write-time-computed and never
  recomputed, same guarantee every other calendar-adjacent feature relies on (R-09).
- A session with no `plan_day_name_snapshot` (an empty/quick-start workout) - day cell
  shows no plan-day label, not a blank/error state.
- Navigating to a month far outside any trained history (e.g. before the user's first
  workout, or into the future) - empty state, not an error.
- A soft-deleted session (`deleted_at` set) - excluded via `v_session_summary`'s own
  filter, verified in the repository integration test.

Not applicable - this project has no feature-flag system (confirmed absent in every

## NFR decisions

Performance: "navigating twelve months is smooth" (roadmap acceptance) is treated as
a benchmark-backed NFR, not left implicit - `yearOverview`'s query is added to the
existing perf benchmark suite against the 75,000-set fixture, same bound class
(`< 150ms`) P11 already established for its own year-range queries
(`muscleGroupVolume`/`exerciseProgression`). No caching/retry/circuit-breaker
concerns apply - this is a local SQLite read, not a network call.
