# UI/UX round 2 - Goals calendar view, chart legibility, avatar, plan fixes

## Problem summary

Second rapid-fire UI/UX batch from live use of the app after the first polish
sweep (PR #29, merged). Investigated live (emulator) and in code before planning;
findings below distinguish confirmed root causes from open design decisions.

## The 9 items, confirmed root causes, and owners

1. **Goals screen should look like Google Calendar**: a day view (default,
   per-goal done/not-done for that day) with a switch to week/month views.
   CONFIRMED: `DailyGoalsScreen.tsx` is currently an undated "today" list with
   no date header or view switcher at all. Data layer is well-positioned:
   `DailyGoalEntry` is already one row per `(goalId, localDate)`, and
   `DailyGoalRepository.listActiveGoalsForWeekday(localDate, weekdayIndex)`
   already answers a single day in one query (currently hardcoded to
   `clock.localDate()`, no date navigation). Week/month need a new repository
   method - no existing single-query path for N goals x M days. frontend-agent,
   Dispatch A.
2. **"Done" badge has an inconsistent color and duplicates the checkbox.**
   CONFIRMED: every other status badge in the app uses `tone="accent"`
   (Plans' Active label, exercise level badge, etc.) - the one outlier is
   `TodayGoalRow.tsx`'s `tone="success"` "Done" badge. For `boolean`-type goals
   it sits right next to a `Checkbox` showing the same state - a true
   duplicate, remove it. For `counter`/`numeric` goals there is no checkbox -
   the badge is currently the only completion signal, so keep it but recolor
   to `tone="accent"`. Same component `TodayGoalRow.tsx` as item 1's day view,
   same dispatch (A) to avoid two dispatches touching one file.
3. **Statistics charts still have no axis description.** CONFIRMED: last
   session's fix (unit-suffixed `formatY`, date-formatted `formatX`) is real
   and wired correctly into victory-native's per-tick labels - the actual gap
   is that there is no *persistent* axis title (e.g. a fixed "kg" label), only
   per-tick values that scroll past with the data and are easy to miss.
   `components/charts/ChartCard.tsx` has a `title`/`subtitle` slot but nothing
   axis-specific. frontend-agent, Dispatch D.
4. **No trend chart for body weight / body-metrics.** CORRECTED premise: a
   chart already exists (`MetricHistoryScreen.tsx`, reachable via
   Profile -> Measurements -> a metric row) but (a) is not discoverable from
   Stats at all, and (b) has *no* axis formatting whatsoever (`formatY` has no
   unit suffix, no `formatX`) - worse off than the Stats charts item 3
   describes. Fix: give `MetricHistoryScreen.tsx` the same axis treatment as
   item 3, and add a body-weight trend card directly on `StatisticsScreen`
   (the single most commonly tracked metric) backed by a new
   `StatisticsRepository` method reading `body_metric_entry` directly by SQL -
   consistent with the existing ADR-0019/0020 precedent of `statistics`
   reading other features' tables directly rather than importing their
   services. Same dispatch as item 3 (D) - both are chart-legibility work and
   the new card reuses whatever axis-title mechanism item 3 introduces.
5. **No charts for daily goals** (completion-rate-over-time for boolean goals,
   value-over-time for counter/numeric goals). CONFIRMED the data layer
   already supports this: `listEntryHistory(goalId, from, to)` returns raw
   per-goal entries, sufficient input for either chart shape. Placement: a new
   `GoalProgressChartCard` added to `GoalFormScreen`'s edit mode, alongside
   the reminders section added last round - no new screen/route needed. Kept
   in `daily-goals` directly (not through `statistics`) since this is a
   feature charting its own data via the cross-feature-agnostic
   `components/charts` primitives, the same way `body-metrics` and
   `workout-logging` already do. frontend-agent, Dispatch C (new files only,
   disjoint from Dispatch A).
6. **No way to update the profile photo after onboarding.** CONFIRMED: not a
   bug in existing wiring - the feature was never built. `ProfileService.
   updateAvatar()` and the repository update are fully implemented and even
   have a passing unit test, but zero hook, zero screen, and zero call site
   exist anywhere - `ProfileScreen.tsx`'s `Avatar` has no `editable`/`onPress`.
   Fix: wire a tap-to-change-photo flow on `ProfileScreen`, reusing the
   already-fixed crop-free `launchImageLibraryAsync` pattern from
   `OnboardingScreen.tsx`. frontend-agent, Dispatch E (isolated to
   `features/profile/**`).
7. **Plans' "Active" badge looks crooked.** CONFIRMED not a rotation/transform
   bug (grepped, none exists) - a layout bug: `PlanCard.tsx` puts the plan
   name (`flex: 1`) and the Badge in the same `Row`; `flex: 1` on a short name
   stretches it to fill all available width, shoving the badge far to the
   right with a large disconnected gap, which reads as "crooked"/misaligned
   rather than sitting next to the name. `PlanEditorHeader.tsx`'s own copy of
   this badge has no such issue (different layout, no `flex:1` sibling). Fix:
   remove `flex: 1` from the name text (or otherwise stop it stretching) so
   the badge sits immediately after the name. frontend-agent, Dispatch F.
8. **Adding multiple exercises at once only adds one** - CONFIRMED as a real,
   already-known bug CLASS, but narrower than reported: Quick Start's own
   exercise picker already supports genuine multi-select and works correctly
   (live-verified: added 4 exercises in one commit). The actual bug is in
   `PlanDayEditorScreen.tsx`'s `handleAddExercise`: an unawaited
   `selectedExerciseIds.forEach(id => addExerciseToDay.mutate(...))` fires all
   inserts concurrently, racing `SqlitePlanRepository.addExerciseToDay`'s
   read-then-insert `sort_order` computation (no unique constraint, so it
   doesn't hard-fail, but it corrupts ordering and can make the UI appear to
   only keep the last one). This exact bug class was already found and fixed
   once in the sibling screen, `ActiveWorkoutScreen.tsx`'s own
   `AddExerciseButton` handler (sequential `for...of` with `await
   mutateAsync`) - but that fix's own code comment claiming
   `PlanDayEditorScreen` was already fixed too is stale/inaccurate; it never
   was. Fix: mirror the already-proven sequential-await pattern into
   `PlanDayEditorScreen.tsx`, and correct the stale comment in
   `ActiveWorkoutScreen.tsx`. Same dispatch as item 7 (F) - both are Plans-
   adjacent, disjoint files from every other dispatch.
9. **Home's "Go to Plans" button is not centered.** CONFIRMED and already
   fixed directly (small, isolated, high-confidence CSS root cause found
   while other dispatches were investigating): `Button` always sets its own
   `alignSelf: 'flex-start'` when not `fullWidth`, which overrides
   `EmptyState`'s `alignItems: 'center'` and left-aligns the action button
   under otherwise-centered title/message text. Fixed in
   `components/feedback/EmptyState.tsx` by wrapping the button in a plain
   content-sized `View` (centered by the parent; the button's own
   `flex-start` makes no visible difference inside a wrapper exactly as wide
   as it is). This is a shared-component fix - it also corrects the same
   latent misalignment in every other `EmptyState` usage with an action
   button (Plans, body-metrics, workout-history, daily-goals, dev gallery),
   which is a pure improvement, not a behavior change, in all of them. No
   dispatch needed - already done and will be verified in the final on-device
   pass alongside everything else.

## Task shape and scaling

Single application, multiple independent-file-set dispatches (5 parallel:
A, C, D, E, F - B is folded into A since it's the same file). Platform:
React Native/Expo, Android-verified on the `gymtracker_test` emulator.

## Step-by-step sequence

1. Dispatch A, C, D, E, F in parallel.
2. Orchestrator: code review each diff (Step 6) - particularly Dispatch A's
   new repository query (SQL correctness, no N+1) and Dispatch F's sequential-
   await fix (matches the proven `ActiveWorkoutScreen.tsx` pattern exactly).
3. On-device verification (Step 7) on the `gymtracker_test` emulator: re-test
   every one of the 9 items live, including the already-applied item 9 fix.
4. Full Jest suite as regression gate (Step 8) - no new tests per standing
   preference, fix only if this sweep breaks something existing.
5. Commit split by dispatch/topic, PR, done - push only with explicit user
   approval.

## Edge cases to address

- Item 1: week/month view's new repository method must handle a goal whose
  `activeWeekdays` bitmask excludes some days in the range (already-proven
  pattern from `listActiveGoalsForWeekday`) - a day a goal isn't active on
  should not render a false "not done" cell for it, it should render nothing/
  skip that goal for that day.
- Item 2: the counter/numeric badge recolor must not remove the ONLY
  completion signal those goal types have - keep it, just recolor.
- Item 4: the new body-weight trend card must handle the empty-data state
  (no body-metric entries logged yet) without crashing - reuse the same
  empty-state pattern other Stats cards already use.
- Item 5: `GoalProgressChartCard` must handle a goal with zero history
  entries yet (freshly created goal) gracefully.
- Item 8: the sequential-await fix must not regress single-exercise adds
  (the common case) - a one-element array must behave identically to today.
