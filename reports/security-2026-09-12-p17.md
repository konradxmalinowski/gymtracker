### [SEC-001] `daily_reminder_response`/`daily_goal_entry` writes from the notification-action handler can throw on a stale foreign key, silently swallowed - INFORMATIONAL
**Category**: Code Quality / Defensive Programming
**Location**: `services/notifications/NotificationScheduler.ts:256-284` (`handleNotificationResponse`)
**Note**: If a user deletes a goal or reminder (hard `purge()`, see SEC-002/finding confirmation below) while one of its notifications is still sitting in the OS notification tray from an earlier schedule, tapping "Zrealizowane"/"Nie" on that stale notification calls `recordResponse`/`recordProgress` with a `reminderId`/`goalId` that no longer exists. `daily_reminder_response.reminder_id` and `daily_goal_entry.goal_id` are both `NOT NULL REFERENCES ... ON DELETE CASCADE`, and this database runs with `foreign_keys=ON`, so the `INSERT` fails with a foreign-key constraint violation. This is caught by the function's own outer `try/catch` and swallowed, matching its documented "never throw, no UI to surface a failure to" contract. This is not a vulnerability (the payload is 100% locally-generated by this same app - see the Focus-area confirmations below - never remote or push-originated, and the failure mode is "the tap silently does nothing" rather than any data corruption or crash), and is exactly the same accepted risk class this codebase's own `ConfirmDialog`-double-tap findings (P8/P9/data-transfer reports) already use: cosmetic UX gap, not a security issue. No fix required; noted for completeness only.

### [SEC-002] Goal/reminder hard-delete purges history with no undo, by design - confirmed correct, not a gap - INFORMATIONAL
**Category**: Data Handling / Architecture
**Location**: `features/daily-goals/services/DailyGoalService.ts:161-163` (`deleteGoal`), `features/daily-goals/services/DailyReminderService.ts:169-171` (`deleteReminder`)
**Note**: Both methods call `repository.purge(id)` (confirmed: `BaseSqliteRepository.purge()` at `repositories/base/BaseSqliteRepository.ts:112-114` is a real, parameterized `DELETE FROM ${this.table} WHERE id = ?`, not a soft delete) - re-verifying the task brief's specific concern about a possible mid-implementation regression back to `softDelete()`. Confirmed not present: neither service calls `softDelete`. This is the correct implementation per the schema's own FK semantics: `daily_goal_entry.goal_id` is `ON DELETE CASCADE` (a deleted goal's history is actually removed, matching `ARCHITECTURE.md` section 7.12) and `daily_reminder.goal_id` is `ON DELETE SET NULL` (a reminder pointing at a deleted goal degrades to standalone rather than being orphaned or itself cascaded away) - both triggers only fire on a real `DELETE FROM`, never on an `UPDATE deleted_at` soft-delete, so a soft-delete implementation here would have silently violated the feature's own acceptance criteria. Recorded as a confirmation, not a finding - this is the codebase's own established "top-level standalone object gets a `ConfirmDialog`-gated, no-undo hard delete" precedent (`PlanService.purgePlan`, `WorkoutSessionService.deleteSession`), applied correctly.

## Focus-area confirmations (no issues found)

- **`SqliteDailyGoalRepository`/`SqliteDailyReminderRepository`**: every query in both files (create/update/list/reorder/upsert/response-record/history) is fully parameterized with `?` placeholders and an array of bound values - no template-literal interpolation of any caller-supplied value into SQL text anywhere in either file. `deleted_at IS NULL` filtering is applied everywhere it needs to be for the parent tables (`daily_goal`, `daily_reminder` - `listAll`, `listByGoalId`, `listActiveGoalsForWeekday`, `listActiveForWeekday`, `reorder`'s per-row `UPDATE`), and correctly *absent* on `daily_goal_entry`/`daily_reminder_response` queries, matching both files' own doc comments and the schema: neither child table has a `deleted_at` column at all (their rows are only ever removed via the parent's `ON DELETE CASCADE`), so filtering on a nonexistent column was never a risk to check for and isn't present. The two upsert methods (`upsertEntryForToday`, `recordResponse`) correctly target their composite unique indexes (`ux_daily_goal_entry_goal_date`, `ux_daily_reminder_response_reminder_date`) via `ON CONFLICT(goal_id, local_date)` / `ON CONFLICT(reminder_id, local_date)` rather than a read-then-write race.
- **CHECK-constraint / Zod-schema alignment**: traced every constraint pair by hand, not assumed from doc comments. `goal_type IN ('boolean','counter','numeric')` <-> `z.enum(GOAL_TYPES)`; `target_value > 0` (when not null) <-> `z.number().finite().positive()`; `CHECK (goal_type = 'boolean' OR target_value IS NOT NULL)` <-> `targetValueMatchesGoalType` refine on create (deliberately not re-checked on a partial update patch, a documented and reasonable scope choice - a partial patch can't know the row's current `goal_type` without a repository read this service layer intentionally avoids, so an inconsistent partial update still fails loudly at the database's own CHECK constraint instead of silently succeeding); `active_weekdays BETWEEN 1 AND 127` <-> `z.number().int().min(1).max(127)` on both goal and reminder schemas; `reminder_type IN ('scheduled','interval')` <-> `z.enum(REMINDER_TYPES)`; `time_of_day GLOB '[0-2][0-9]:[0-5][0-9]'` <-> a stricter `/^([01]\d|2[0-3]):([0-5]\d)$/` regex (correctly disallows `29:59`, which the raw SQL GLOB alone would accept - the Zod layer is the tighter of the two, so nothing invalid reaches the DB); `interval_minutes >= 15` <-> `z.number().int().min(15)`; the reminder-type XOR CHECK (`scheduled` needs `time_of_day` and no `interval_minutes`, `interval` needs the reverse) <-> `reminderTypeFieldsAreValid` refine, applied on both create *and* update (stricter than the goal-type case, appropriately - noted directly in that schema's own comment). No gap either direction: nothing only-CHECK-constraint-catches, and nothing only-Zod-catches that the DB would then silently accept in an inconsistent state.
- **`NotificationScheduler.ts` cancellation scoping**: `cancelForReminder()` (lines 145-157) calls `getAllScheduledNotificationsAsync()` and cancels only identifiers starting with `idPrefixFor(reminderId)` = `daily-reminder-${reminderId}-`; it never calls `cancelAllScheduledNotificationsAsync()` anywhere in the file (confirmed via full-file read, not a grep-only check). Cross-checked both other independent notification wrappers for prefix collisions: `WorkoutReminderService.ts` uses `workout-reminder-day-${day}` (`NOTIFICATION_ID_PREFIX = 'workout-reminder-day-'`) and also never calls the cancel-all API; `features/rest-timer/services/RestTimerNotificationService.ts` never sets an explicit `identifier` on its `scheduleNotificationAsync()` call at all, so `expo-notifications` assigns it a random UUID - no fixed prefix to collide with either of the other two. All three prefixes/schemes are disjoint; none of the three modules ever calls the destructive cancel-all API.
- **Notification-action write path is locally-originated only**: confirmed this is a fully offline app with no push-notification capability anywhere in the codebase - `grep -rn "getExpoPushTokenAsync|ExponentPushToken|expo-server-sdk"` across `services/`, `features/`, and `app/` returns zero matches. Every notification `handleNotificationResponse` can ever receive was scheduled locally by `scheduleRemainingOccurrencesToday` in the same module, with `data.reminderId`/`data.goalId` populated from the `DailyReminder` row this app itself wrote to its own database, not from any external or attacker-controlled source - there is no network/IPC/deep-link path that could inject a fabricated notification response into this handler.
