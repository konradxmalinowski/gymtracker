## Informational notes

### [SEC-INFO-01] `PhotoDetailScreen.handleSaveEdit` has no error handling around `updatePhoto.mutateAsync`
**Category**: Code quality / error handling
**Location**: `features/body-metrics/screens/PhotoDetailScreen.tsx:79-86` (`handleSaveEdit`), called from `onPress={() => void handleSaveEdit()}` at line 238
**Detail**: Unlike `MeasurementQuickEntrySheetContent.handleSubmit` (which wraps its `mutateAsync` call in `try/catch` and shows a translated `formError`), `handleSaveEdit` has no `try/catch`. The note field (`TextField` at line 208) has no `maxLength` prop, so a user can type past `PHOTO_NOTE_MAX_LENGTH` (1000 chars); saving then throws `ProgressPhotoValidationError` from the service layer with no catch at the call site. Effect: no error is shown, the screen is left stuck in `isEditing` mode (since `setIsEditing(false)` only runs after a successful `await`), and the rejected promise from the `void`-called async function is unhandled. Not a security issue (no path/stack-trace leakage - the error is simply dropped, not displayed) and not reachable through any file I/O or SQL path; it's an offline, single-local-user app with no attacker-controlled input reaching this code, so at most a self-inflicted UX dead end.
**Impact**: None security-relevant. Local usability gap only - the user has to back out and re-enter edit mode after trimming a too-long note, or force-close, with no message explaining why "Save" appeared to do nothing.
**Fix** (optional, non-blocking): wrap `handleSaveEdit`'s body in `try/catch` (mirroring `MeasurementQuickEntrySheetContent.handleSubmit`) and/or add `maxLength={PHOTO_NOTE_MAX_LENGTH}` to the `TextField`.

### [SEC-INFO-02] Both new repositories are fully parameterized; no injection surface
**Category**: Injection / SQL
**Location**: `features/body-metrics/repository/SqliteBodyMetricRepository.ts`, `features/body-metrics/repository/SqliteProgressPhotoRepository.ts`
**Detail**: Every query in both files (including `listByMetric`'s `metric` filter, `listAll`'s `pose` filter, and `listLatestPerMetric`'s window-function query) binds every value as a `?` parameter via `executor.select`/`insertRow`/`updateRow`. No template-literal interpolation of any caller-supplied value into SQL text anywhere in either file (the only string interpolation is `${limitSql}`, which is the pre-built, whitelisted `LIMIT ?/OFFSET ?` fragment from `repositories/query/buildLimitOffset`, itself parameterized). `metric`/`pose` are also closed Zod enums (`BODY_METRIC_TYPES`, `poseSchema`) validated one layer up in the service before ever reaching the repository. Confirmed non-exploitable, consistent with every prior phase's repository review.

### [SEC-INFO-03] File-naming and path handling confirmed safe against traversal; no user-controlled path segments
**Category**: Path traversal / file I/O
**Location**: `services/files/ExpoFileStorage.ts:8-14` (`pathSegments`), `features/body-metrics/services/ProgressPhotoService.ts:109-119` (`addPhoto`'s `fileName`/`thumbName` construction)
**Detail**: `pathSegments()` splits on `/`, drops empty segments, and throws on any literal `.`/`..` segment - applied uniformly by every `ExpoFileStorage` method, including the new `list()`. The photo file-naming scheme (`${id}.jpg` / `${id}-thumb.jpg`) uses only the `IdGenerator`-produced UUIDv7 `id` (never user-supplied text - no filename, note, or pose value ever becomes part of a path), and the directory constant (`PROGRESS_PHOTO_DIRECTORY` / `PHOTOS_DIRECTORY`, both the literal `'progress-photos'`) is a hardcoded string, not user input, in both the service and the repository's independent copy of that same literal (documented in `SqliteProgressPhotoRepository.ts`'s own header comment as a deliberate non-shared duplication, consistent with this codebase's established "repository never imports its feature's service layer" rule). `list()`'s own `relativePath` argument is likewise always the hardcoded `PHOTOS_DIRECTORY` constant at its one call site (`verifyIntegrity()`), never a value derived from a row or route param. No path-traversal surface found.

### [SEC-INFO-04] ADR-0012 write-then-commit / delete ordering correctly followed in both new services
**Category**: Data integrity / file-DB consistency
**Location**: `features/body-metrics/services/ProgressPhotoService.ts:105-162` (`addPhoto`), `:198-207` (`permanentlyDeletePhoto`)
**Detail**: `addPhoto` processes both images, copies them into `FileStorage`, and verifies non-zero `size()` for both the full image and the thumbnail **before** `repository.create()` is ever called - matching ADR-0012 exactly (a failure at any point before the final `create()` call leaves at most an orphan file with no row, never a row pointing at a missing file). `permanentlyDeletePhoto` correctly follows the documented reverse ordering for deletion: it looks up the row (`findByIdIncludingDeleted`), calls `repository.purge(id)` first, and only then deletes the two files from disk - so a failure partway through leaves at most an orphan file, never a dangling row. This is the same ordering the task description flagged as already fixed by code review in this method; re-verified correct by this pass. `BodyMetricService` has no file I/O at all (pure SQL via `BodyMetricRepository`), so ADR-0012 ordering does not apply to it - confirmed by reading the full file, not assumed.
