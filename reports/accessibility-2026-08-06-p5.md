## Findings

### [A11Y-P5-001] `DraggableList`'s move-up/move-down accessibility actions never reach a native accessibility node in any real P5 consumer - **BLOCKING**, REPORT ONLY
**Category**: Gesture accessibility / operable - this is the mandatory gate
**Location**: `components/gestures/DraggableList.tsx`'s `attachMoveActions` (lines 167-203) and its call site in `DraggableRow` (line 339), combined with `components/gestures/PressScale.tsx` and `features/plans/components/{PlanCard,PlanDayCard,PlanDayExerciseRow}.tsx`

**The mechanism, read in isolation, is correct** - and I want to be precise about that, because the failure is not in the reasoning `DraggableList.tsx`'s own comments lay out. `attachMoveActions` clones `accessible`/`accessibilityActions`/`onAccessibilityAction` onto whatever single element `renderItem` returns, exactly mirroring `SwipeableRow.tsx`'s `attachAccessibilityActions`. The boundary logic is correct (`index > 0` for `moveUp`, `index < itemCount - 1` for `moveDown`), and `handleMoveAction` calls the exact same `onDragEnd`/`commitReorder` path (`components/gestures/DraggableList.tsx:96-108`, `:328-337`) a completed drag gesture calls - confirmed by reading `commitReorder`'s array-splice logic and `DraggableList`'s render prop wiring (`onDragEnd: commitReorder`, line 126).

**The failure is in what `renderItem` actually returns in the three real screens.** `attachMoveActions` clones the accessibility props onto the *top-level JSX element* `renderItem` produces - which, in all three usages, is `<PlanCard>`, `<PlanDayCard>`, or `<PlanDayExerciseRow>` (`PlanListScreen.tsx:130`, `PlanDetailScreen.tsx:171`, `PlanDayEditorScreen.tsx:263`), never a bare `View`/`Pressable`/`Text`. None of these three components accept or forward `accessible`/`accessibilityActions`/`onAccessibilityAction` - their prop interfaces (`PlanCardProps`, `PlanDayCardProps`, `PlanDayExerciseRowProps`) declare a fixed, closed set of named props, and their function bodies destructure only those names with no `...rest` spread. The cloned props exist on the JSX element's prop object at runtime, but the component that receives them simply never reads them, so they go nowhere. Even if they did forward them, the inner control each of these three components actually renders is `PressScale` (`components/gestures/PressScale.tsx`), whose own `PressScaleProps` interface *also* has no `accessible`/`accessibilityActions`/`onAccessibilityAction` fields and whose body forwards only its own named list of accessibility props (`accessibilityRole`, `accessibilityLabel`, `accessibilityHint`, `accessibilityState`) to the underlying `Pressable`. Two independent points of loss, either one sufficient on its own to break this.

**Empirical proof** (not just static reading): I wrote a throwaway RNTL test mounting `DraggableList` with the *real* `PlanCard` component as `renderItem` - the exact same wiring `PlanListScreen.tsx` uses - and searched the rendered `toJSON()` tree for any node carrying an `accessibilityActions` prop.

```
NUMBER OF NODES WITH accessibilityActions PROP: 0
```

Zero. Compare this to `DraggableList.test.tsx`'s own passing tests (see A11Y-P5-003 below), which use `renderItem={(item) => <Text>{item.name}</Text>}` - a bare React Native `Text`, which *does* accept and forward arbitrary accessibility props straight to its native host component, because it's a core RN component, not a custom one with a closed prop interface. The test suite is accidentally exercising a code path none of the three real screens use.

**Compounding factor for superset-grouped exercises**: `PlanDayEditorScreen.tsx`'s `renderItem` (lines 261-289) wraps grouped exercises in `<SupersetGroupEditor>` instead of returning `PlanDayExerciseRow` directly. `SupersetGroupEditorProps` (`features/plans/components/SupersetGroupEditor.tsx:8-11`) declares only `group`/`children`/`testID` and, like the row components, has no prop pass-through - so even in a hypothetical world where `PlanCard`/`PlanDayCard`/`PlanDayExerciseRow` were fixed to forward these props, grouped day-exercises would still separately need `SupersetGroupEditor` fixed, since it's the element `attachMoveActions` actually clones onto for those rows.

**Net effect**: in the shipped app, a VoiceOver/TalkBack or switch-control user has no way to reorder a plan, a plan's days, or a day's exercises - the exact gap CLAUDE.md's "Known gaps" section names this phase as required to close. The gap is not closed; it is invisible in code review because the mechanism *looks* right and its own unit tests pass.

**Why this isn't a small fix**: closing it requires deciding how accessibility props flow through custom row components that already have closed, purpose-built prop interfaces - at minimum, `PressScale` needs `accessible`/`accessibilityActions`/`onAccessibilityAction` added to its interface and forwarded to the underlying `Pressable` (which does support them natively - RN's `Pressable` accepts both), and then `PlanCard`/`PlanDayCard`/`PlanDayExerciseRow`/`SupersetGroupEditor` each need either an explicit accessibility-passthrough prop or a `...rest`-style forward to their own `PressScale`/wrapping `View`. That's a real design decision about this component family's prop contract, not a one-line patch - reporting rather than fixing directly, per this audit's scoping rules (same reasoning the P1 audit used for A11Y-004/A11Y-005).

### [A11Y-P5-002] `dragHandle="handle"` mode's handle is nested inside the row's own already-`accessible` `PressScale`, likely making it (and its `adjustable` role/label) unreachable as an independent VoiceOver/TalkBack stop - HIGH, REPORT ONLY (needs on-device verification)
**Category**: Gesture accessibility / operable, focus order
**Location**: `features/plans/components/PlanCard.tsx:44-52`, `PlanDayCard.tsx` (equivalent shape), `PlanDayExerciseRow.tsx:62-71`, combined with `components/gestures/DraggableList.tsx:282-315`

All three real consumers use `dragHandle="handle"` (not `"row"` - confirmed in `PlanListScreen.tsx:127`, `PlanDetailScreen.tsx:166`, `PlanDayEditorScreen.tsx:257`), so `DraggableList` builds a separate handle element (`Animated.View`, `accessible`, `accessibilityRole="adjustable"`, `accessibilityLabel="Drag to reorder"`, wrapped in its own `GestureDetector`) and passes it into `renderItem` as the `dragHandle` argument. Every one of the three row components renders this handle **inside** their own outer `PressScale` (`{dragHandle ? <View>{dragHandle}</View> : null}` as the first child of the `Row` that `PressScale` wraps) - and that outer `PressScale` is itself `accessible` (RN's `Pressable` defaults `accessible` to `true`) with its own `accessibilityRole="button"`/`"checkbox"` and `accessibilityLabel`.

This is exactly the anti-pattern this codebase's own comments (`SwipeableRow.tsx:131-153`, `DraggableList.tsx:154-166`) go to real lengths to avoid for the row's *own* primary interaction - a container marked `accessible` collapses its subtree into one opaque node on both iOS and Android's accessibility trees. Here the collapse risk isn't the row's primary action losing its handler (that's unaffected - `onPress` still fires); it's the *nested* handle's own separately-declared `accessible`/`accessibilityRole="adjustable"`/`accessibilityLabel` becoming unreachable as its own stop, since the outer row is already claiming the whole subtree as a single accessible unit.

I could not independently confirm this from RNTL - `getAllByRole('adjustable', ...)` and `queryAllByLabelText('Drag to reorder')` both found the handle node fine when mounted through the real `PlanCard`, because RNTL's tree inspection reads component props directly and does not simulate the native accessibility engine's subtree-collapsing behavior (this is the same limitation `reports/accessibility-2026-08-05-p1.md`'s A11Y-004 called out for `SwipeableRow`). This needs verification with VoiceOver/TalkBack on a real device or the platform accessibility inspectors before it can be called either "fine" or "broken" with certainty - flagging as a real, plausible risk given the codebase's own stated understanding of this exact failure mode, not a confirmed defect.

**Secondary, lower-severity note in the same location**: even setting reachability aside, the handle's `accessibilityRole="adjustable"` still promises a swipe-up/swipe-down increment/decrement interaction the handle itself doesn't implement - the actual working alternative (once A11Y-P5-001 is fixed) is a `moveUp`/`moveDown` **custom action pair on the row**, not an increment/decrement handler on the handle. This is the same role/behavior mismatch P1's A11Y-005 flagged ("adjustable... with no matching behavior") - P5 correctly built the row-level custom-action alternative A11Y-005 asked for, but didn't reconcile it with the handle's pre-existing, still-unbacked `adjustable` role claim.

### [A11Y-P5-003] `DraggableList.test.tsx`'s accessibility tests validate the cloning mechanism against a synthetic child, never against any of the three real row components - HIGH, REPORT ONLY
**Category**: Test coverage / false confidence
**Location**: `__tests__/components/gestures/DraggableList.test.tsx:128-181`

These are real, well-constructed tests - not superficial "renders without crashing" checks. The boundary-conditions test (lines 128-153) correctly asserts the first row omits `moveUp`, the last omits `moveDown`, and middle rows have both. The reorder test (lines 155-181) correctly fires `onAccessibilityAction` with `actionName: 'moveUp'` on the middle row and asserts `onReorder` was called with the same reordered array (`['2', '1', '3']`) a completed drag would produce. Both are genuine behavioral assertions, and both pass.

The problem is what they're asserting *against*: every test in this file uses `renderItem={(item) => <Text>{item.name}</Text>}` - a bare React Native `Text` element. As established in A11Y-P5-001, `Text` is a core RN component that accepts and forwards arbitrary accessibility props to its native host view, unlike `PlanCard`/`PlanDayCard`/`PlanDayExerciseRow`, which have closed prop interfaces that silently drop them. This means the test suite proves `attachMoveActions`'s cloning logic is *internally* correct, but provides zero coverage of whether that logic actually reaches a real consumer - which, per A11Y-P5-001's empirical check, it does not, in all three shipped screens. A reviewer reading only the test file (as the task brief anticipated an implementing agent's report might invite) would reasonably conclude the gate is satisfied; it isn't. Recommend either an additional test that renders through one of the real `features/plans/components` row types, or - more robustly - a shared "accessible row" test helper other future `DraggableList`/`SwipeableRow` consumers can be checked against, so this class of gap is caught before merge rather than by a follow-up audit.

### [A11Y-P5-004] Multi-select "N selected" count relies solely on the Android-only `accessibilityLiveRegion` - MEDIUM, **FIXED**
**Category**: Perceivable / transient content
**Location**: `features/plans/screens/PlanDayEditorScreen.tsx` (select-mode action bar), `features/exercise-library/screens/ExercisePickerScreen.tsx` (picker's selection bar)

Both screens' "N selected" `Text` had only `accessibilityLiveRegion="polite"` - the same Android-only mechanism P1's A11Y-002 found and fixed on `Toast`/`ErrorState`/`TextField` (`accessibilityLiveRegion` maps to `android:accessibilityLiveRegion` and has no iOS counterpart; RN's only cross-platform way to announce dynamic text to VoiceOver is the imperative `AccessibilityInfo.announceForAccessibility()` call). As shipped, a VoiceOver user selecting/deselecting exercises in either the day editor's "Group" flow or the exercise picker would never hear the running count change - silent on iOS, exactly the failure mode A11Y-002 already documented and fixed elsewhere in this codebase.

**Fix applied**: added a `useEffect` in each screen that calls `AccessibilityInfo.announceForAccessibility()` with the same localized count string whenever the selection changes, alongside (not replacing) the existing `accessibilityLiveRegion` prop - identical shape to A11Y-002's fix. In `PlanDayEditorScreen.tsx` the effect is gated on `selectMode` so it doesn't fire before the user has entered select mode; `ExercisePickerScreen.tsx`'s selection bar is always visible, so its effect fires on every `selectedIds` change including the initial mount (a truthful "0 selected" on screen open, not a false announcement).

### [A11Y-P5-005] Checkbox semantics, disabled-state conveyance, and icon-only button labels - PASS
**Category**: Roles/labels/touch targets - confirming what already works, not a defect

Checked explicitly per the task brief and found correct, no fix needed:
- `PlanDayExerciseRow.tsx`'s select-mode rows and `ExercisePickerScreen.tsx`'s picker rows both set `accessibilityRole="checkbox"` and `accessibilityState={{ checked: selected }}` on the outer `PressScale` *and* on the nested `Checkbox` primitive (`components/ui/Checkbox.tsx`, which already sets `accessibilityRole="checkbox"`/`accessibilityState={{ disabled, checked: value }}` correctly on its own `Pressable`) - a VoiceOver user hears "checkbox, checked/unchecked" correctly either way they focus the row.
- The "Group" action bar's button (`plan-day-group-button`) is a `Button` (`components/ui/Button.tsx`), which forwards `disabled` into `accessibilityState={{ disabled: isDisabled, busy: loading }}` via its own `PressScale` - VoiceOver correctly announces it as disabled when fewer than 2 rows are selected (`disabled={selectedIds.size < 2}`, `PlanDayEditorScreen.tsx:322`).
- Every icon-only `IconButton` across `PlanCard`/`PlanDayCard`/`PlanDayExerciseRow`/`PlanEditorHeader` (set-active/rename/duplicate/delete/ungroup/remove) has a required, dynamic `accessibilityLabel` (e.g. `t('plans.list.deleteAccessibilityLabelTemplate', { name: plan.name })`) - `IconButton`'s own type makes the prop non-optional (P1's design decision, `components/ui/IconButton.tsx:26`), so there's no way any of these call sites could have shipped unlabeled.
- Touch targets: every `IconButton` in scope uses `size="sm"` (32pt visual) with `IconButton`'s own `Math.max(hitSlop.small, (44 - dimension) / 2)` formula (`= 8pt/side`), giving a 48pt effective target - clears the 44pt bar. `Checkbox` is 24pt visual with `hitSlop.default` (12pt/side), giving 48pt effective. `DraggableList`'s own handle (32pt) uses the identical formula (`HANDLE_HIT_SLOP`, `DraggableList.tsx:37`) via `Gesture.hitSlop()` for its *pan* recognition area - confirmed this is the gesture-recognition hit area, not the View's own `hitSlop` prop (Gesture Handler doesn't read that), a distinction the file's own comment gets right. All rows themselves are 72-76pt tall (`ROW_HEIGHT`/`76` constants in the three screens), far above the 44pt floor.

### [A11Y-P5-006] Move-up/move-down action labels have no row-position context - LOW, informational, not fixed
**Category**: Label quality
**Location**: `components/gestures/DraggableList.tsx:320-325`, `i18n/catalogs/en.ts:54-56`

The two custom actions are labeled with the fixed strings `"Move up"`/`"Move down"` (`t('draggableList.moveUpAccessibilityLabel')`/`moveDownAccessibilityLabel`), not something like "Move up, currently position 3 of 8." This is a minor UX consideration, not a defect: the actions surface through VoiceOver's rotor "Actions" menu, which is entered *after* focus has already landed on and announced the row itself (which carries its own identifying `accessibilityLabel`, e.g. the plan/day/exercise name) - so a user has already heard "which row" before reaching "Move up"/"Move down" in that row's actions list. Position-within-list context would be a nice-to-have refinement once A11Y-P5-001 is actually fixed and this becomes reachable at all, not a blocking gap on its own.

## Recommendations, priority order

1. **Blocking, before this phase can be considered to satisfy CLAUDE.md's mandatory gate**: resolve A11Y-P5-001. This requires: (a) adding `accessible`/`accessibilityActions`/`onAccessibilityAction` to `PressScaleProps` and forwarding them to the underlying `Pressable`; (b) threading the same through `PlanCard`/`PlanDayCard`/`PlanDayExerciseRow`'s own prop interfaces down to their `PressScale`; (c) doing the same for `SupersetGroupEditor` for the superset-grouped case. All three are mechanical once the prop-contract decision is made, but the decision itself (how far this passthrough pattern should generalize - just these components, or a shared prop type every `DraggableList`/`SwipeableRow`-wrapped row component should adopt) is exactly the kind of call this audit is scoped to report, not make unilaterally.
2. **Before this phase ships**: get real-device VoiceOver/TalkBack (or Accessibility Inspector/Scanner) confirmation on A11Y-P5-002 - if the handle is confirmed unreachable as its own stop, its role/label/gesture may need to move to living entirely on the row's own accessible node instead of a nested child, once A11Y-P5-001's fix is in place to test it against.
3. **Recommended alongside the A11Y-P5-001 fix**: extend `DraggableList.test.tsx` (or add a sibling test) that mounts against a real `features/plans/components` row type, per A11Y-P5-003, so this specific gap can't recur silently in a future phase that adds a fourth consumer.
4. (Optional, low priority) A11Y-P5-006 - add position context to the move-action labels once they're actually reachable.

## Sign-off

This audit does **not** clear P5 to commit as-is with respect to the accessibility gate CLAUDE.md names for this phase. The fix as implemented is conceptually sound and passes its own unit tests, but empirical verification against the real `PlanCard`/`PlanDayCard`/`PlanDayExerciseRow` components - the actual code path every one of the three shipped screens uses - shows zero accessibility-action nodes reach the rendered tree. The tracked "Known gaps" item (`DraggableList` gesture-only, no non-gesture reorder alternative) is not closed by this diff; it is currently just harder to notice, because the component-level mechanism and its tests both look correct in isolation. The one fix applied directly in this pass (A11Y-P5-004, the multi-select announcement gap) is additive, non-breaking, and verified against the full relevant test slice with no regressions.
