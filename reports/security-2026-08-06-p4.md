## Checklist Results

### 1. SQL injection / query construction - PASS
`SqliteExerciseRepository.ts` was read in full. Every value-position in every query is bound as a `?` parameter - no string interpolation of caller/user-supplied values into SQL text anywhere in the file.

- Multi-select `IN` lists: `buildFilterClause()`'s `equipmentSlugs`/`bodyParts` filters go through `repositories/query/WhereClause.ts`'s `inList()`, which generates `column IN (?, ?, ...)` with one placeholder per value and returns the fixed `NEVER` (`1=0`) clause for an empty list rather than emitting `IN ()` or matching everything.
- `EXISTS` subqueries: the `muscleSlugs` filter (line 337-343) builds `EXISTS (SELECT 1 FROM exercise_muscle em WHERE em.exercise_id = e.id AND em.muscle_slug IN (?, ?, ...))` with `query.muscleSlugs` bound as `params`, not interpolated - the `?` placeholders are generated via `.map(() => '?').join(', ')`, count matches the bound array length.
- `buildContextClause()` (line 366-372) selects between two hardcoded column names (`is_gym`/`is_home`) via a ternary on `ExerciseContext`, a closed TypeScript union (`'gym' | 'home'`) - not a caller-controlled string reaching SQL text.
- **FTS5 `buildFtsMatchQuery()` (line 130-136)** - this is the one function in scope that string-manipulates user search text before it becomes part of a SQL parameter's *content*, so it got focused attention. It splits on whitespace, and for every token replaces `"` with `""` (doubling - the correct FTS5/SQL string-literal escape for an embedded quote) and wraps the result in `"..."*`  (a quoted phrase with a trailing prefix-match operator). Verified this defeats FTS5 query-syntax injection, not just SQL injection: any FTS5 operator a user might type - `OR`, `NOT`, `NEAR`, `AND`, a `column:` filter, unbalanced parens - becomes a literal quoted string once wrapped, because FTS5 does not parse operators or column filters inside a double-quoted string. Traced the escaping through a couple of edge cases by hand (a token that is itself just `"`, an empty-after-trim `text`) and both resolve to valid, inert FTS5 syntax. The resulting `matchQuery` string is then passed as `params[0]` to `executor.select(sql, [matchQuery, ...])` (line 325-329) - bound via `?` against `exercise_fts MATCH ?`, never concatenated into the SQL string itself. Correct on both axes (SQL parameterization and FTS5 query-syntax neutralization).
- `repositories/query/WhereClause.ts` and `OrderAndPage.ts` (used by this file and generically by the rest of the app): every value-producing helper (`eq`, `neq`, `isNull`, `gte`, `lte`, `like`, `inList`) binds via `?`; `buildOrderBy()` validates any column name against a caller-supplied whitelist and throws on an unlisted column rather than trusting it; `buildLimitOffset()` clamps `limit`/`offset` and binds both as parameters. This feature's repository does not call `buildOrderBy()` (its sort order is hardcoded `ORDER BY ... ASC`), so that path isn't exercised here, but the primitive itself is sound.
- `upsertUserDataColumns()` (line 524-569) builds a dynamic `SET`/`INSERT` column list, but the column names always come from a fixed, hardcoded `Record<string, SqlParam>` object built by the three callers (`setFavorite`/`setNote`/`setDefaultRest`), never from an arbitrary caller-supplied key set - same pattern the P3 audit already verified in `SqliteProfileRepository.update()`.

### 2. Input validation coverage / no repository bypass - PASS
`grep -rn "repository\|Repository"` across `features/exercise-library/hooks/*.ts` and `features/exercise-library/screens/*.tsx`/`components/*.tsx` returns zero imports of `SqliteExerciseRepository`, `ExerciseRepository`, or a relative `../repository/...` path (the only hits are unrelated doc-comment prose mentioning "the repository"). `features/exercise-library/index.ts` (the barrel) exports only `ExerciseService` and its types/errors - `ExerciseRepository`/`SqliteExerciseRepository` are never re-exported, so there is no accidental one-import path to bypass validation. `ExerciseService.createCustom()`/`updateCustom()` run their Zod schemas (`createCustomExerciseSchema`/`updateCustomExerciseSchema`) before ever calling the repository; `setNote()`/`setDefaultRest()` likewise validate through `noteSchema`/`restSecondsSchema` first. Confirmed the `exercise-library` architecture-layering zone is actually registered in `eslint.config.js` (not just a doc comment) - `'exercise-library'` appears in the generated feature list that drives the "no direct repository access from presentation" and "cross-feature barrel-only" ESLint rules.

### 3. Business-rule enforcement (only `source = 'custom'` editable/deletable) - PASS
Enforced at the repository layer, not just hidden in the UI. `SqliteExerciseRepository.updateCustom()` (line 411-478) and `deleteCustom()` (line 480-500) both load the existing row first and check `existingRow.source !== 'custom'` (respectively `existing.source !== 'custom'`), throwing `ExerciseNotEditableError` before any mutation happens. This runs unconditionally for every caller of `updateCustom`/`deleteCustom`, regardless of how the id was obtained - a direct deep link to `/exercises/edit/:id` for a catalog exercise reaches `ExerciseFormScreen`, which does render an edit form initially (after `useExercise` resolves) but any submit attempt would hit this same repository check via `ExerciseService.updateCustom()` -> `updateCustom()`. The form screen additionally short-circuits this case with its own explicit guard (`existing.data.source !== 'custom'` at line 230, rendering a generic error state before the form even renders) - correctly documented in the surrounding comment as defense-in-depth on top of the repository-level check, not a substitute for it.

### 4. Deep link / route parameter handling - PASS
`app/(tabs)/exercises/[id].tsx` and `edit/[id].tsx` both pull `id` from `useLocalSearchParams` and pass it straight to `useExercise(id)` / `ExerciseFormScreen`. `useExercise()` guards a missing id with `enabled: Boolean(id)`, so it never fires a query for `undefined`. For a malformed or nonexistent id, `SqliteExerciseRepository.findById()` returns `null` (a `selectOne` miss, not a thrown error), which the service passes through unchanged. `ExerciseDetailScreen` renders three distinct states in order - `isPending` (skeleton), `isError` (generic pre-translated `exerciseLibrary.detail.loadErrorMessage`), and `!exercise` (generic pre-translated `exerciseLibrary.detail.notFoundMessage`) - none of which render `error.message`, a stack trace, or the raw id back to the UI. `ExerciseFormScreen`'s edit mode mirrors this (`existing.isError || !existing.data` -> same generic error state). No crash path found for a garbage id.

### 5. File-path handling (`getExerciseImageSource`) - PASS
Confirmed against the actual implementation, not assumed. `assets/exercises/imageMap.ts` is a fully static, generated module: 1740 lines of `'<filename>.webp': require('./<filename>.webp')` literals, one per bundled image, produced by `scripts/build-exercise-image-map.ts` at build time specifically because Metro cannot resolve a dynamic `require(variablePath)` - the header comment on both files makes this constraint explicit. `getExerciseImageSource(filename)` (`assets/exercises/index.ts`) does `exerciseImageMap[filename]`, a plain object-key lookup against this static map, returning `undefined` for any unrecognized key - there is no `fs.readFile`/`Paths.join`/filesystem access at runtime anywhere in this path, so there is no traversal surface: a filename that isn't an exact key (whatever its content - `../../etc/passwd`, empty string, etc.) simply misses the lookup and returns `undefined`. `ExerciseImageGallery.tsx` handles the `undefined` case with a placeholder icon tile rather than crashing.

Confirmed the second half of the question too: `ExerciseFormScreen.tsx`'s submit handler builds its `CreateCustomExerciseInput` payload (line 156-164) from `nameEn`, `namePl`, `equipmentSlug`, `bodyPart`, `level`, `instructions`, `muscles` only - `images` is never set, so the UI has no path today to populate a custom exercise's `images` array. `CreateCustomExerciseInput.images` remains theoretically writable at the type/service level (Zod's `images: z.array(z.string()).optional()`), but no current caller reaches it - worth a one-line note for whichever future phase (if any) adds a custom-exercise image picker: at that point `images` would carry an app-generated filename (mirroring how P3's avatar filenames are `IdGenerator`-generated, never user-typed), not a raw path, so `getExerciseImageSource`'s miss-returns-`undefined` behavior would still degrade safely even then.

## Additional notes (informational, not findings)

- `database/seed/loadCatalogAsset.ts` and `services/container.ts`/`app/_layout.tsx`'s catalog-seed wiring were reviewed per the task's explicit scope note. Both read a bundled, build-time-generated JSON asset via `require('../../assets/data/exercises.catalog.json')` and wire dependency injection (`SqliteExerciseRepository`/`ExerciseService` construction) - no user input, no external data source, no injection surface. `runSeed()` is described as idempotent in the boot-sequence comment; not independently re-verified here since `catalogSeeder`/`runSeed` themselves are outside this phase's diff (pre-existing P2 code) and out of the stated scope.
- Error classes (`ExerciseNotEditableError`, `ExerciseValidationError`, `ExerciseDeleteBlockedError`) carry structured data (exercise id, Zod issues, blocking plan names) for `instanceof`-based handling, consistent with the P3-established pattern (`InvalidNicknameError`). None of this data is sensitive in an offline, no-auth, no-PII-beyond-locally-entered-nickname app, and UI surfaces only ever render pre-translated generic messages, never `error.message` directly - same conclusion as the P3 report's boot-sequence note.
- `ExerciseDeleteBlockedError`/`ExerciseNotEditableError` messages do get logged via `logging?.info('exercise.delete.blocked', ...)` on a blocked delete - this is a local, on-device log call (`services/logging`), not a network call, consistent with the app's no-backend architecture; not a data-exfiltration concern.
