## Focus Area Results

### 1. `SqliteStatisticsRepository.ts` - parameterization and `deleted_at`/`status` filtering - PASS

Read all six methods in full.

- `volumeByPeriod`/`exerciseProgression`/`yearlyHeatmap` query `v_working_set` directly. That view (`database/schema.sql`, unchanged in this diff) already bakes in `ws.deleted_at IS NULL AND ws.is_completed = 1 AND s.deleted_at IS NULL AND s.status = 'completed'` at the view definition, so every row these three methods see is already correctly filtered - confirmed by reading the view definition, not assumed from its name.
- `sessionFrequency`/`durationTrend` query `workout_session` directly (not through a view) and each carries its own explicit `status = 'completed' AND deleted_at IS NULL` clause inline.
- `muscleGroupVolume` joins `exercise` onto `v_working_set` (`JOIN exercise e ON e.id = vs.exercise_id`) for `body_part`. See INFO-001 below - the join has no explicit `e.deleted_at IS NULL`, but this has no correctness or security impact given how soft delete works on this table.
- Every caller-supplied value (`localDateFrom`, `localDateTo`, `exerciseId`, `year`-derived date strings) is bound as a `?` parameter in every query. No template-literal interpolation of a variable into a SQL clause anywhere in the file - confirmed by reading every query string, not by grepping for a pattern that could miss a variant. The one `${year}-01-01`/`${year}-12-31` string build (`yearlyHeatmap`) interpolates only inside a plain JS string that is itself passed as a bound array element, never concatenated into the SQL text - `year` also isn't caller/route input in this diff, see section 2.

`resolveOneRmFormula` (private, `exerciseProgression`'s `metric === 'e1rm'` path only) calls `this.deps.settings.get('oneRm.formula', tx)` through the shared `SettingsRepository`, which is itself Zod-validated with default-fallback (per this codebase's standing settings-repository contract) - not a fresh, unvalidated read.

**Verdict: full parameterization on every query; correct `deleted_at`/`status` filtering (via the view for three methods, inline for two); no injection surface.**

### 2. `oneRm.formula` settings resolution - PASS, confirmed byte-identical in intent to the established precedent

Compared `SqliteStatisticsRepository.resolveOneRmFormula` (lines 213-216) against `SqlitePersonalRecordRepository.resolveFormula` (`features/records/repository/SqlitePersonalRecordRepository.ts:204-207`) side by side:

```ts
// SqliteStatisticsRepository.resolveOneRmFormula
const key = await this.deps.settings.get('oneRm.formula', tx);
return key === 'brzycki' ? brzyckiFormula : epleyFormula;

// SqlitePersonalRecordRepository.resolveFormula
const key = await this.deps.settings.get('oneRm.formula', tx);

```

Identical resolution logic, identical settings key, identical fallback-to-Epley default. `resolveOneRmFormula` is only invoked when `metric === 'e1rm'` (the class's own doc comment states this and the call site in `exerciseProgression` confirms it via the ternary in `Promise.all`) - `top_set`/`volume` metrics never touch settings at all. No new surface: this reuses an existing, already-reviewed settings key and read path rather than introducing a second one.

**Verdict: correct reuse, no new surface.**

### 4. Route params / new user-facing input - PASS (none exists)

`app/(tabs)/stats/exercise/[exerciseId].tsx` is a thin wrapper (`app/` never contains screen bodies, per this codebase's own rule); `ExerciseProgressionScreen.tsx` reads `exerciseId` via `useLocalSearchParams<{ exerciseId: string }>()` and uses it two ways, both safe: (a) `exerciseService.getById(exerciseId!)`, a bound argument into the already-parameterized `SqliteExerciseRepository` query layer, unchanged by this diff; (b) passed into `useExerciseProgression`, which threads it as a bound `?` parameter into `exerciseProgression()` (section 1 above) and as a plain array element of a TanStack Query cache key, never concatenated into SQL or a route string. `enabled: exerciseId !== undefined` guards both queries against an unhydrated route param, mirroring `usePreviousPerformance`'s established P8 pattern.

`routes.stats.exercise(exerciseId)` builds a typed Expo Router `Href` object (`{ pathname, params: { exerciseId } }`), the same pattern `routes.history.detail`/`routes.modals.planDayPicker` already use - no hand-built/concatenated route string. The only call site constructing this route (`app/(tabs)/exercises/[id].tsx:132`) passes an `exerciseId` that itself originated from the exercise-detail screen's own already-validated route param, not free text.

Beyond `exerciseId`, this phase's only other user-facing control is `StatRangeSelector` (a closed four-value enum, `STAT_RANGES = ['4w','3m','1y','all']`, typed as `StatRange`) and a metric toggle (`ProgressionMetric`, a closed union) - neither is free text, neither reaches SQL as anything but a lookup key into `RANGE_BUCKET`/`RANGE_DAYS` (`features/statistics/domain/statRange.ts`) before being converted to bound date-string parameters. `generateBucketBoundaries` (`dateRangeBuckets.ts`) loops between `localDateFrom`/`localDateTo` at day/week/month granularity - reviewed for unbounded-loop/DoS risk given it's control-flow driven by these dates, but `resolveStatRange`'s `'all'` case is capped at a fixed floor (`ALL_TIME_FLOOR_LOCAL_DATE = '2000-01-01'`) bucketed by month, so the worst case is roughly (current year - 2000) x 12 iterations (low hundreds), not attacker-influenced since the range is a closed enum, not free-form dates. No form, no text input, nothing OWASP-relevant beyond the checks above - correctly matches the user's own framing of this phase as "read-only, no forms."

**Verdict: no injection or DoS surface in the new route param or range/metric selectors.**

## Additional notes (informational, not findings)

- **INFO-001**: `muscleGroupVolume`'s `JOIN exercise e ON e.id = vs.exercise_id` has no explicit `e.deleted_at IS NULL` filter, despite the class's own header doc comment stating `exercise` "is filtered explicitly in `muscleGroupVolume` since the view doesn't join it." Read `exercise`'s schema (`database/schema.sql:67-87`) to check the actual impact: `deleted_at` is a soft-delete marker only - the row itself is never removed, and IDs are UUIDs with no reuse - so a soft-deleted custom exercise's historical sets still correctly resolve `body_part` through this join; nothing is silently dropped or misattributed, and there is no way for the missing filter to cause a wrong id to match (unlike a hard-delete-and-reinsert scheme, which this codebase doesn't use). This is a doc-comment/code mismatch worth a one-line fix for accuracy, not a security or data-integrity issue - flagged for awareness, not blocking.
- **INFO-002**: `eslint.config.js`'s `FEATURES` array already listed `'statistics'` before this phase (it was one of the pre-existing empty-skeleton feature directories P0-P10 already declared), so the "no direct repository access from presentation" and "cross-feature imports only through a barrel" rules already covered `features/statistics` with zero diff needed here - confirmed via `git diff main -- eslint.config.js` (empty) plus reading the array directly, not assumed from the feature now having real files.
- **INFO-003**: `services/container.ts`'s new `statisticsRepository` member has no accompanying service, by design (documented in its own doc comment, the same "flat DTOs, nothing to validate" shape `exerciseHistoryRepository`/`homeDashboardRepository` already established) - every query is parameterized at the repository layer itself (section 1), so the missing service layer is not an unvalidated-input gap.
- **INFO-004**: Grepped every new/changed non-test file in this diff (`features/statistics/**`, `components/charts/**`) for `console\.(log|warn|error)`, `eval(`, `dangerouslySetInnerHTML`, `WebView`, and `new Function(` - zero hits. This is an offline, single-local-user app with no accounts and no cross-user authorization boundary (consistent with every prior phase's report) - `exerciseId` flowing through this diff's one new route param is not an IDOR concern for the same reason P9/P10's reports already gave for their own route params.
