## Findings

### [A11Y-P7-001] `RestTimerBar`'s decrease/open-settings/increase controls collapse into one inert accessibility node - **BLOCKING**, REPORT ONLY
**Category**: Operable / gesture accessibility - screen-reader reachability of the bar's primary controls
**Location**: `features/rest-timer/components/RestTimerBar.tsx:126-188` (the single `<View>` passed as `SwipeableRow`'s only child, wrapping `AdjustDeltaButton` (decrease), the countdown `PressScale` (tap-to-adjust/open-settings), and `AdjustDeltaButton` (increase)), combined with `components/gestures/SwipeableRow.tsx:153-171` (`canAttachToChild`/`attachAccessibilityActions`)

`RestTimerBar` renders:

```tsx
<SwipeableRow rightAction={skipAction} testID={testID}>
  <View style={{ flexDirection: 'row', ... }}>
    <AdjustDeltaButton symbol="−" ... />       {/* decrease, own Pressable */}
    <PressScale onPress={onOpenSettings} ... />  {/* countdown / open settings */}
    <AdjustDeltaButton symbol="+" ... />       {/* increase, own Pressable */}
  </View>
</SwipeableRow>
```

`SwipeableRow`'s own file header (lines 131-153) is explicit about the failure mode this is supposed to avoid: "putting `accessible={true}` on an ancestor `View` would collapse that whole subtree into one opaque accessibility node." Its `attachAccessibilityActions` path (used here, since `RestTimerBar`'s child is a single valid element, `Children.count === 1`, so `canAttachToChild` is `true`) is designed for exactly one safe case: *the child passed in is itself already a coherent single interactive unit* - its own comment says so verbatim: "children is normally something with its own primary interaction (e.g. a pressable `ListRow`)... The child keeps whatever `accessible` value it already has (a `Pressable` defaults it to `true` on its own, so reachability comes for free)."

`RestTimerBar` violates that precondition. The `<View>` it hands to `SwipeableRow` is a bare layout `View` (default `accessible={false}`, no `onPress` of its own), not a `Pressable`/`PressScale`, and it wraps **three separate, unrelated interactive controls** rather than one. `attachAccessibilityActions` (`SwipeableRow.tsx:239-258`) clones `accessible: childProps.accessible ?? true` onto it - i.e. forces it to `true` - and attaches only the swipe/rotor action (`{ name: 'rightAction', label: 'Skip rest' }`). The result:

- The whole row becomes one accessibility element on both iOS and Android (RN's own documented `accessible` contract: "groups its children into a single selectable component").
- That single element has **no `accessibilityLabel` of its own** and, critically, **no `onPress`/activation handler of its own** - it is a plain `View`. Whatever the exact native engine details of "do the nested `Pressable`s' own labels leak through," double-tap/standard activation on this merged node has nothing on the `View` itself to trigger. This part does not depend on device-specific collapsing ambiguity: the merged node is a dead end for activation regardless of how nested-label leakage resolves on a given OS version.
- The only thing a screen-reader user can do with this row is reach "Skip rest" through the rotor/custom-actions menu. The decrease (-15s), increase (+15s), and tap-to-adjust/open-settings (`RestTimerSettingsSheet`) actions - the bar's actual primary functionality - are not reachable through standard screen-reader navigation.

This is worse than, and not covered by, the accepted "Known gap" in `CLAUDE.md` about `DraggableList`'s handle (`A11Y-P5-002`): that gap concerns a *secondary* nested icon losing independent reachability inside a row whose outer container was *deliberately* built as a single accessible unit with its own correct label and a working primary `onPress` - double-tapping that row still does the right thing. Here, the merged node is not deliberate (nothing in `RestTimerBar` sets `accessible` itself; it's a side effect of `SwipeableRow`'s clone), has no label, and has no primary action of its own to fall back on - all three of the row's actual controls are affected, not one secondary one.

This also was not caught by this phase's own code-review pass - the pass's documented fix (`RestTimerBar.tsx:82-92`) is specifically about the announcement-cadence/re-anchor bug (see A11Y-P7-002), not this structural issue, and no test in the repository renders `RestTimerBar` through `SwipeableRow` to catch it (see A11Y-P7-003).

**Suggested fix direction** (not applied - report only, per this task's scope): `SwipeableRow` already documents the correct usage pattern - hand it a single element that is *itself* meant to be one accessible unit. Concretely, pass only the countdown/open-settings `PressScale` as `SwipeableRow`'s child (it already has its own correct `accessibilityRole`/`accessibilityLabel`/`accessibilityHint`, and is a real `Pressable` so `attachAccessibilityActions` will merge the skip action onto it exactly as designed), and render the two `AdjustDeltaButton`s as siblings outside the swipeable region instead of inside it. This is a straightforward layout change with a well-precedented target shape (mirrors how `SwipeableRow`'s own doc comment describes its intended single-primary-interaction usage) - unlike the `DraggableList` handle gap, it does not require on-device verification to decide *whether* to attempt it, only to confirm the result once applied.

### [A11Y-P7-002] Countdown announcement cadence and upward-adjustment re-anchor - **PASS** (re-verified correct, not assumed)
**Category**: Perceivable / live-region behavior - the specific code-review fix this task asked to be re-checked
**Location**: `features/rest-timer/components/RestTimerBar.tsx:64-106`, `stores/restTimerStore.ts:60-82`

Traced this by hand rather than trusting the inline comment. The effect's `shouldAnnounce` condition is:

```ts
isExpired || last === null || remainingSeconds > last || last - remainingSeconds >= ANNOUNCE_INTERVAL_SECONDS
```

Verified three cases:
1. **Ordinary countdown (no adjustment)**: `remainingSeconds` is monotonically non-increasing between adjustments (`selectRemainingSeconds` derives strictly from `deadlineAt - now`, and `now` only advances - `stores/restTimerStore.ts:68-74`), so `remainingSeconds > last` can never be true here; announcements fire only every `ANNOUNCE_INTERVAL_SECONDS` (15s) as intended, not every 250ms tick. Confirmed no per-tick spam: once `isExpired` becomes `true`, `remainingSeconds` clamps to `0` (`Math.max(0, ...)`) and stays there, so neither `remainingSeconds` nor `isExpired` changes value on subsequent ticks - React's dependency comparison (`[deadlineAt, remainingSeconds, isExpired]`) means the effect does not re-run on every subsequent 250ms tick after expiry, so the "expired" announcement fires exactly once, not repeatedly.
2. **Upward adjustment** (the bug this fix targets): increasing `deadlineAt` (via the bar's own "+15s" button, or picking a longer preset in `RestTimerSettingsSheet`) increases `remainingSeconds` past `last`. `remainingSeconds > last` catches this unconditionally (not gated by the 15s interval), correctly re-anchoring `last` and re-announcing immediately - this is what prevents the described bug ("a single upward adjustment permanently pins `last` above where `remainingSeconds` can ever reach again while only counting down"). Confirmed this resolves it: after the re-anchor, `last` equals the new (higher) `remainingSeconds`, so the normal 15s-interval countdown cadence resumes correctly from the new baseline.
3. **Downward adjustment**: with `ADJUST_DELTA_SECONDS === ANNOUNCE_INTERVAL_SECONDS` (both `15`), any decrease always satisfies `last - remainingSeconds >= 15` on its own, so this path was never actually broken by the bug being fixed - the fix's necessity is specific to the upward-adjustment direction, consistent with its own comment.

No spam, no silently-stuck cadence. This part of the diff is correct as shipped.

### [A11Y-P7-003] No component-level accessibility test coverage exists for any of P7's new UI components - HIGH, REPORT ONLY
**Category**: Test coverage / false confidence
**Location**: `__tests__/features/rest-timer/` (only `services/RestTimerNotificationService.test.ts` exists) and `__tests__/stores/restTimerStore.test.ts` - no test file renders `RestTimerBar`, `TimerPresetChips`, `RestTimerSettingsSheet`, `TimerSettingsScreen`, or `ActiveWorkoutBanner`'s new rest-countdown half through React Native Testing Library at all

This is exactly the contributing condition `reports/accessibility-2026-08-06-p5.md`'s `A11Y-P5-003` named for the equivalent P5 gap: a well-reasoned, self-consistent accessibility mechanism (here, `SwipeableRow`'s child-cloning contract) that looks correct in isolation and ships unverified against its real, concrete consumer. P5's eventual fix for the analogous bug was paired with integration tests mounting the *real* row components (`PlanCard`/`PlanDayCard`/`PlanDayExerciseRow`), specifically because a synthetic `<Text>` stand-in had previously hidden the same class of gap. Recommend the same discipline here once A11Y-P7-001 is fixed: a test that mounts `RestTimerBar` for real and asserts which nodes in the rendered tree carry `accessible`/`accessibilityActions`/`onPress`, so a future refactor of `RestTimerBar` or `SwipeableRow` can't silently reintroduce the collapse.

### [A11Y-P7-004] `ProgressRing`'s `accessibilityRole="progressbar"`/`accessibilityValue` never reaches a screen reader inside `RestTimerBar` - LOW, informational, not fixed
**Category**: Redundant/inert semantics, not a defect in itself
**Location**: `features/rest-timer/components/RestTimerBar.tsx:158-163` (`<ProgressRing>` nested inside the countdown `PressScale`), `components/ui/ProgressRing.tsx:40-46`

`ProgressRing` sets `accessibilityRole="progressbar"` and `accessibilityValue={{ min: 0, max: 100, now: ... }}` on its own outer `View`, but does not set `accessible={true}` itself - and it is nested inside `RestTimerBar`'s countdown `PressScale`, which is already `accessible` (a `Pressable` defaults to `true`) with its own explicit `accessibilityLabel` (the formatted countdown text). Per RN's accessibility-element contract, a nested element's own role/value only becomes independently reachable if it is itself an accessibility element outside an already-accessible ancestor's collapsed subtree; here it is not, so the ring's percentage is never exposed to VoiceOver/TalkBack on its own. This is harmless in the current design - the ancestor's `accessibilityLabel` already conveys the same information as readable text ("90s rest remaining"), which is more useful to a screen-reader user than a bare percentage - so no fix is needed unless a future design wants the ring to be independently announced.

### [A11Y-P7-005] Touch targets, roles/state, color contrast, dynamic type, and `ActiveWorkoutBanner` design - PASS
**Category**: Confirming what already works, not a defect

Checked explicitly against this task's stated concerns and found correct:
- **Touch targets**: `AdjustDeltaButton` (`RestTimerBar.tsx:191-223`) is 36x36 visual with `hitSlop.small` (8pt/side, `theme/tokens.ts:162`), giving a 52x52pt effective target - clears the 44pt floor. `Chip` (`components/ui/Chip.tsx`, `md` size = 36pt height) uses the same `hitSlop.small` pattern, also 52pt effective - used by both `TimerPresetChips` instances. The countdown `PressScale` (`flex: 1`, `paddingVertical: space[3]` plus the 40pt `ProgressRing`) is comfortably larger than 44pt in both dimensions. Native `Switch` rows (`TimerSettingsScreen.tsx`) use the OS's own accessible control, not a custom hit target. Minor, non-blocking note: `AdjustDeltaButton`'s 8pt hitSlop and the row's `space[3]` (12pt) gap between adjacent elements leave only ~4pt of separation between two adjacent controls' expanded hit regions - not a WCAG target-*size* violation (each control independently clears 44pt), just a slightly tight margin worth being aware of if the row's spacing ever shrinks further.
- **Roles/state**: `Switch` (`components/ui/Switch.tsx:29-31`) sets `accessibilityRole="switch"` and `accessibilityState={{ disabled, checked: value }}` correctly for all four `TimerSettingsScreen` toggles (sound/vibration/notifications/auto-start). `Chip` sets `accessibilityRole="button"` and `accessibilityState={{ disabled, selected }}` correctly for every preset in both `TimerPresetChips` call sites. `ActiveWorkoutBanner`'s `PressScale` sets `accessibilityRole="button"` with a single, correctly-composed `accessibilityLabel` that includes title, elapsed time, and (when running) rest-remaining time (`i18n/catalogs/en.ts:390-392`).
- **Color contrast** (computed by hand from `theme/tokens.ts` hex values, WCAG relative-luminance formula): `color.success` (`#3DDC84`) text/ring on `color.backgroundElevated` (`#0F0F12`) ≈ 10.7:1; `color.accent` (`#4C8DFF`) ring stroke on the same background ≈ 6.0:1; `color.textInverse` (`#09090B`) text/icons on `color.accent` (`#4C8DFF`) in `ActiveWorkoutBanner` ≈ 6.2:1. All comfortably clear WCAG AA (4.5:1 text, 3:1 non-text UI graphics) with margin to spare.
- **Dynamic type**: `Text` (`components/ui/Text.tsx`) sets no `allowFontScaling={false}`/`maxFontSizeMultiplier` cap anywhere in scope, so the countdown numerals, chip labels, and settings-row text all scale with the system font size by default, per RN's normal behavior. Not verified at 200% scale on a real device/simulator (none available in this environment, the same constraint every prior phase's write-up has flagged) - `RestTimerBar`'s countdown `Row` does use `flex: 1`/`justify="space-between"` rather than fixed widths, which should reflow reasonably, but this is unverified rather than confirmed.
- **`ActiveWorkoutBanner`'s rest-countdown half** (`features/workout-logging/components/ActiveWorkoutBanner.tsx:102-144`) is correctly designed as a *single* accessible action (navigate back to the active workout) rather than repeating `RestTimerBar`'s per-control mistake - there is exactly one logical action here, so wrapping the whole banner in one `accessible` `PressScale` with one composed label is the right shape, not an instance of A11Y-P7-001's anti-pattern.
- **`TimerSettingsScreen`'s loading announcement** (`TimerSettingsScreen.tsx:36-40`) correctly uses `AccessibilityInfo.announceForAccessibility()` (not just a platform-limited `accessibilityLiveRegion`), matching the fix pattern P1's `A11Y-002` and P5's `A11Y-P5-004` already established elsewhere in this codebase.

## Recommendations, priority order

1. **Blocking, before this phase can be considered to satisfy WCAG operable/reachability requirements for its own headline component**: fix A11Y-P7-001. Concretely: stop passing a multi-child, non-interactive `<View>` as `SwipeableRow`'s sole child in `RestTimerBar`; attach the swipe/skip action to the countdown `PressScale` alone (already a real `Pressable` with its own correct role/label), and render the two `AdjustDeltaButton`s as siblings outside the swipeable region.
2. **Recommended alongside the fix**: add a test (per A11Y-P7-003) that mounts the real `RestTimerBar` (not a synthetic stand-in) and asserts that the decrease/open-settings/increase controls each carry their own independent `accessible`/`onPress`/`accessibilityLabel`, not a single merged ancestor node - so this class of gap can't recur silently, matching the discipline P5's `A11Y-P5-003`/its own follow-up fix established.
3. **Before this phase ships, if practical**: real-device VoiceOver/TalkBack confirmation of the fix once applied - the exact "does the merged node still get focus with no action" claim in A11Y-P7-001 is confirmable from source alone (no `onPress` on the ancestor), but confirming the *positive* case (each of the three controls is now independently reachable and correctly labeled) is worth a quick device pass, consistent with this project's own bar for this class of fix.
4. (Optional, low priority) A11Y-P7-004 - no action needed unless a future design wants the progress ring's percentage independently announced.

## Sign-off

This audit does **not** clear P7 to commit as-is with respect to screen-reader reachability of `RestTimerBar`'s primary controls. The countdown-announcement cadence/re-anchor fix this task specifically asked to be re-verified **is correct** - traced by hand against `restTimerStore`'s tick/clamp semantics, not assumed from the inline comment. However, a structural issue outside that fix's scope - `RestTimerBar` handing `SwipeableRow` a multi-control `View` instead of a single coherent interactive child - collapses the bar's decrease/open-settings/increase controls into one inert accessibility node, leaving only the swipe-to-skip action reachable via screen reader. This is a confirmed-from-source defect (the collapsed node has no `onPress` of its own regardless of native subtree-collapsing ambiguity), distinct from and more severe than the already-accepted, device-unverifiable `DraggableList` handle gap tracked in `CLAUDE.md`. All other checked surfaces (`TimerPresetChips`, `RestTimerSettingsSheet`, `TimerSettingsScreen`, the modal/route wrappers, and `ActiveWorkoutBanner`'s new rest-countdown half) pass: correct roles/state, adequate touch targets, sufficient color contrast, unrestricted dynamic-type scaling, and (for `ActiveWorkoutBanner`) a correctly-scoped single-action design that does not repeat `RestTimerBar`'s mistake.
