## Checklist Results

### 1. SQL injection / query construction - PASS
`SqlitePlanRepository.ts` was read in full, every `t.run`/`t.select`/`t.selectOne` call site included. Every value-position is bound as a `?` parameter - no string interpolation of caller-supplied *values* into SQL text anywhere in the file.

- **`setSupersetGroup`'s `IN (...)` placeholder generation** (line 535, `dayExerciseIds.map(() => '?').join(', ')`) - the placeholder *count* is derived from the array length (safe, standard pattern - same technique already verified in the P4 report for `loadExerciseSummaries`/`loadDaysForPlan`), and the actual id *values* are always bound via `[...dayExerciseIds]`/`[...dayExerciseIds]` in the two queries that use it (the membership `SELECT` and the final `UPDATE`), never concatenated into the SQL string. Same pattern reused in `loadDaysForPlan` (`plan_day_exercise WHERE plan_day_id IN (${placeholders})`) and `loadExerciseSummaries` (`exercise WHERE e.id IN (${placeholders})`) - all bind values as params.
- **Dynamic table names in the private `insertInto`/`updateRowIn`/`softDeleteRow`/`restoreRow`/`nextSortOrder` helpers** - confirmed these are never caller/user-controlled. The `table` parameter's type is the closed union `PlanChildTable = 'plan_day' | 'plan_day_exercise'` (plus the additional `'plan'` literal for `nextSortOrder`), and grepping every call site in the file confirms each passes one of these two/three literal strings directly (`this.insertInto('plan_day', ...)`, `this.softDeleteRow('plan_day_exercise', ...)`, etc.) - never a variable sourced from a method argument, request body, or route param. TypeScript's closed union enforces this at compile time for any future caller too. This is the same interpolation-safety reasoning `BaseSqliteRepository.ts`'s own header comment documents for `this.table`, correctly extended by this file's own doc comment (lines 108-121) to the two child tables the shared base class can't cover (it's hardwired to one `table` per instance). Verified against `BaseSqliteRepository.ts` directly (`insertRow`/`updateRow`/`softDelete`/`restore`/`purge`) - identical pattern, `this.table` is always the subclass's own hardcoded field.
- Every `UPDATE ... WHERE id = ?`/`WHERE plan_id = ?`/`WHERE plan_day_id = ?` across `setActivePlan`, `reorderPlans`, `reorderDays`, `reorderDayExercises`, `addDay`, `addExerciseToDay`, `updateDayExercise` binds its id(s) as parameters, never interpolated.
- `updateDayExercise`'s dynamic `SET` column list (line 458-467, mirrors `updateRowIn`/`upsertUserDataColumns`'s pattern already verified in the P4 report) builds its `Record<string, SqlParam>` from a fixed set of hardcoded keys (`target_sets`, `target_rep_min`, ...), never from an arbitrary caller-supplied key set - the patch's *values* go through Zod first (see check 2) and are bound as `?` regardless.

### 2. Input validation boundary / no repository bypass - PASS
`grep -rn "SqlitePlanRepository\|PlanRepository"` across the full repo (excluding `__tests__`) returns hits only inside `features/plans/repository/*`, `features/plans/services/PlanService.ts` (type-only import plus doc-comment prose), `features/plans/index.ts` (doc-comment prose explaining why it's *not* re-exported), and `services/container.ts` (the one allowed composition-root wiring point). No screen, component, or hook imports `SqlitePlanRepository`/`PlanRepository` directly. `features/plans/index.ts`'s barrel exports only `PlanService` and its types/errors - `PlanRepository`/`SqlitePlanRepository` are never re-exported, consistent with the `exercise-library` precedent the P4 report already verified.

Every mutating `PlanService` method that takes free-form input (`createPlan`, `renamePlan`, `addDay`, `addExerciseToDay`, `updateDayExercise`) runs its Zod schema (`checkWithSchema`/`parseWithSchema`) before ever touching `this.deps.repository`. Schemas map directly to the DB's own `CHECK` constraints (`target_sets BETWEEN 1 AND 50`, `target_rpe BETWEEN 1 AND 10`, `target_rep_min <= target_rep_max`) rather than inventing separate bounds, so a validation gap can't silently diverge from what the schema itself would reject at the SQL layer. `setSupersetGroup`'s minimum-size check (`SupersetMinimumSizeError`) is a deliberate, documented split of responsibility with the repository's own same-day check (`SupersetSpansMultipleDaysError`) - both layers enforce a real invariant, neither is dead code.

### 3. Transaction correctness / atomicity - PASS (with one LOW note, see Additional notes)
Every multi-statement repository method (`createPlan`, `duplicatePlan`, `setActivePlan`, `addDay`, `duplicateDay`, `addExerciseToDay`, `updateDayExercise`, `reorderPlans`/`reorderDays`/`reorderDayExercises`, `setSupersetGroup`) follows the same `tx ? runner(tx) : this.deps.db.transaction(runner)` composition pattern, so calling any of them standalone always wraps its statements in one transaction, and calling it from a future caller that already holds a `tx` joins that outer transaction rather than opening a second one. Traced `db.transaction()`'s actual implementation (`database/client.ts`'s `ExpoSqlExecutor.transaction()`, pre-existing P2 infrastructure, not part of this diff but load-bearing for this phase's correctness claims): it delegates to `expo-sqlite`'s `withExclusiveTransactionAsync`, which rolls back automatically if the callback throws - a crash or thrown error mid-`duplicatePlan` (e.g. after the new `plan` row insert but before every `plan_day`/`plan_day_exercise` copy completes) leaves the whole operation rolled back, not a half-copied plan.
- `setActivePlan`'s clear-then-set ordering (documented in its own doc comment) is correct: `ux_plan_single_active` is a partial unique index checked per-statement, and clearing the old active row before setting the new one means there is never a committed or intra-transaction moment with two active rows - a moment with zero is fine, only "more than one" is forbidden.
- `duplicatePlan`/`duplicateDay` generate fresh ids for every copied row (via `insertRow`/`insertInto`'s own `this.generateId()`) and copy `exercise_id` as-is (exercises are referenced, never duplicated) - matches the aggregate-copy contract in both methods' own doc comments.
- `setSupersetGroup`'s membership `SELECT` (verifying all ids exist and share one `plan_day_id`) and its subsequent `UPDATE` run inside the same transaction/callback, so there's no window for another write to invalidate the check between the two statements in this single-threaded, single-user app - see the LOW note below for the one nuance worth flagging on this exact pair of statements.

### 4. Soft-delete / `deleted_at IS NULL` filter coverage - PASS
Checked every `SELECT`/`UPDATE` in the file for a forgotten filter:
- `listPlans`, `getPlan`, `addDay`, `addExerciseToDay`, `duplicateDay`, `hydrateDay`, `loadDaysForPlan`, `updateDayExercise`'s read-back, and every `reorder*`/`rename*` `UPDATE` all filter on `deleted_at IS NULL` (or, for `restoreRow`, the inverse `IS NOT NULL`) as appropriate.
- **`loadExerciseSummaries`** deliberately omits `e.deleted_at IS NULL` on the `exercise` join - this is explained in the file's own comment (lines 654-659) and is correct, not an oversight: a `plan_day_exercise` row's `exercise_id` is protected from ever pointing at a soft-deleted custom exercise by `ExerciseService`'s own `listReferencingPlans` delete guard (verified as real, repository-level enforcement in the P4 report, not just a UI check), and a hard delete is blocked entirely by the schema's `ON DELETE RESTRICT` on that FK. Showing the referenced exercise's current data regardless of its own `deleted_at` is the documented, deliberate choice for the one theoretical stale-reference edge case, not a data leak of unrelated rows.
- **`setSupersetGroup`'s final `UPDATE ... WHERE id IN (${placeholders})`** (line 552) has no `deleted_at IS NULL` filter, unlike the membership `SELECT` immediately above it in the same method. Not exploitable as a security issue - the ids were already verified non-deleted by that same-transaction `SELECT` a few lines earlier, and this is a single-user, single-writer, offline app with no concurrent client that could soft-delete one of those rows between the two statements inside one exclusive transaction. Noting for completeness since the task asked specifically about this filter; recommend adding `AND deleted_at IS NULL` to that `UPDATE` anyway as defense-in-depth/consistency with every other write in the file, not because a concrete exploit path exists.

### 5. Deep link / route parameter handling - PASS
`app/(tabs)/plans/[planId].tsx` and `app/(tabs)/plans/[planId]/day/[dayId].tsx` (via `PlanDetailScreen`/`PlanDayEditorScreen`'s `planId`/`dayId` props) both go through `usePlan(id)`, which guards a missing id with `enabled: Boolean(id)` - same pattern the P4 report verified for `useExercise`. For a malformed or nonexistent id, `PlanService.getPlan()` -> `SqlitePlanRepository.getPlan()` returns `null` (a `selectOne` miss), not a thrown error; both screens render a generic, pre-translated not-found state (`plans.detail.notFoundMessage`/`plans.day.notFoundMessage`) rather than `error.message` or the raw id. `PlanDayEditorScreen` additionally guards `!day` (the day not existing inside a plan that does exist, e.g. a stale link to an already-deleted day) with the same generic not-found branch. No crash path found for a garbage `planId`/`dayId`.

### 6. Error message surfacing - PASS
`PlanValidationError.issues[0]?.message` is rendered directly to form-error text in `PlanListScreen`/`PlanDetailScreen`/`PlanDayEditorScreen` (e.g. "Plan name is required."). This differs from the P4 report's exercise-library screens (which never render `error.message`), but is not a finding: every message a user can see this way is one of this file's own static, hardcoded Zod schema strings (`'Plan name is required.'`, the rep-range refinement message, etc.) - never a reflection of raw user input, a stack trace, or any data from the database. There is no injection or information-disclosure surface here (this is a local-only app with no other user to disclose information to), just a UX choice to show the specific validation reason instead of a generic message.

### 7. Zustand picker store / data-return mechanism - INFORMATIONAL (not a security finding)
`stores/exercisePickerStore.ts` holds a single in-flight `request` (`alreadySelectedIds` + `onConfirm` callback), opened by `PlanDayEditorScreen.handleAddExercise()` immediately before `router.push()` into `(modals)/exercise-picker`, and cleared by the modal itself on confirm (`close()` then `router.back()`) or defensively on a `null` request (a route reached some other way, e.g. a stale deep link, backs out immediately rather than rendering a broken picker). This is a singleton, so a second `open()` call before the first flow's modal has closed would silently replace the pending request - not reachable in the current UI (the modal is the only consumer that can call `open()`, and it's pushed synchronously right after `open()`), but worth knowing if a second call site (the P6 active-workout screen this store's own header comment says is coming) opens the picker from a different flow while one is already in-flight. This is a UX/correctness note, not a security issue - no sensitive data crosses this store (exercise ids only), and there's no cross-user or cross-session leakage risk in an offline single-user app.

One related note on the picker's *consumer* side: `handleAddExercise`'s `onConfirm` closure (`PlanDayEditorScreen.tsx` line 182-187) calls `addExerciseToDay.mutate({ dayId: day.id, input: { exerciseId } })` once per selected id in a plain `forEach`, not awaited and not batched into one repository call. See the LOW finding below.

## Findings

### [SEC-001] Multi-select "add exercises to day" is not one atomic transaction - LOW
**Category**: Local data integrity / business logic
**Location**: `features/plans/screens/PlanDayEditorScreen.tsx:178-189` (`handleAddExercise`'s `onConfirm` closure)
**Reproduction**: Open a plan day, tap "Add exercise," multi-select 5 exercises in the picker, confirm. `onConfirm` runs `selectedExerciseIds.forEach((exerciseId) => addExerciseToDay.mutate({ dayId: day.id, input: { exerciseId } }))` - five independent calls into `PlanService.addExerciseToDay()`, each of which opens and commits its own transaction via `SqlitePlanRepository.addExerciseToDay()`'s `tx ? runner(tx) : this.deps.db.transaction(runner)`. If the app is killed (OS memory pressure, crash, forced close) after the 2nd of 5 commits, the day ends up with exactly 2 of the 5 selected exercises added - a partially-applied "add 5 exercises" action rather than all-or-nothing.
**Impact**: Data integrity only, not a security vulnerability - the app is offline/single-user, so there's no confidentiality/authorization exposure. Worst case is a confusing partial state the user has to notice and fix by hand (nothing crashes, no corruption of the schema's own invariants - each individual `addExerciseToDay` call is itself atomic and valid). Low likelihood in practice (the window is only open between two of several near-instantaneous local SQLite commits) and low severity given the offline, no-payment, no-compliance nature of this data.
**Fix**: Either (a) add a batch method to `PlanRepository`/`PlanService` (e.g. `addExercisesToDay(dayId, inputs[])`) that loops inside one `this.deps.db.transaction(runner)` call, mirroring how `duplicatePlan`/`duplicateDay` already loop multiple inserts inside one transaction, or (b) if a batch method isn't worth adding for a rare multi-select flow, at minimum `await` each `addExerciseToDay.mutateAsync(...)` sequentially in the `onConfirm` closure instead of firing all `mutate()` calls unawaited - this doesn't make the whole batch atomic but at least makes the partial-failure window deterministic (all exercises up to the failure point committed, none after) rather than relying on unspecified interleaving of concurrent unawaited mutations.
