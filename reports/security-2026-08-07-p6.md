## Checklist Results

### 1. SQL injection / query construction - PASS
Read `SqliteWorkoutSessionRepository.ts` in full (1360 lines), every `t.run`/`t.select`/`t.selectOne`/`tx.run` call site included.

- Every value-position across all 19 repository methods (`findInProgress`, `startFromPlanDay`, `startEmpty`, `finish`, `discard`, `setSessionNotes`, `addExercise`, `removeExercise`, `restoreExercise`, `reorderExercises`, `setSupersetGroup`, `setExerciseNote`, `appendSet`, `addDropSet`, `updateSet`, `completeSet`, `uncompleteSet`, `deleteSet`, `restoreSet`, `saveActiveState`) binds caller-supplied values as `?` parameters. No string interpolation of a *value* into SQL text anywhere in the file.
- **`setSupersetGroup`'s `IN (...)` placeholder generation** (line 663, `sessionExerciseIds.map(() => '?').join(', ')`) and **`loadExerciseSummaries`'s** equivalent (line 1100) - same pattern the P4/P5 reports already verified for the same technique in `SqlitePlanRepository`/`SqliteExerciseRepository`: only the placeholder *count* comes from array length, the id *values* are always bound (`[...sessionExerciseIds]`/`[...exerciseIds]`), never concatenated.
- **Dynamic table names in `insertInto`/`updateRowIn`** (the `session_exercise`/`workout_set` equivalents of `BaseSqliteRepository`'s single-table helpers) - the `table` parameter's type is the closed union `SessionChildTable = 'session_exercise' | 'workout_set'`. Grepped every call site in the file: each passes one of these two literal strings directly, never a variable derived from a method argument. Same interpolation-safety reasoning already established for `SqlitePlanRepository`'s `PlanChildTable` in the P5 report, correctly reused here and documented in the file's own header comment (lines 289-293).
- `saveActiveState`'s dynamic `INSERT ... ON CONFLICT DO UPDATE SET` (lines 965-995) builds its column list from a fixed set of hardcoded keys (`session_id`, `focused_session_exercise_id`, `scroll_offset`, `updated_at`) filtered by `patch`'s own optional fields - never from an arbitrary caller-supplied key set, and every value is bound positionally.

### 2. Input validation boundary / no repository bypass - PASS
`grep -rn "SqliteWorkoutSessionRepository\|WorkoutSessionRepository"` across the repo (excluding `__tests__`) returns hits only inside `features/workout-logging/repository/*`, `features/workout-logging/services/WorkoutSessionService.ts` (type-only import), `features/workout-logging/index.ts` (doc-comment prose explaining why it is *not* re-exported), and `services/container.ts` (the one allowed composition-root wiring point). The barrel's `export {}` block only surfaces `WorkoutSessionService`, types, errors, and pure domain calculators - `WorkoutSessionRepository`/`SqliteWorkoutSessionRepository` are never re-exported, matching the `plans`/`exercise-library` precedent.

Every mutating `WorkoutSessionService` method that takes free-form input runs its Zod schema before ever touching `this.deps.repository`: `appendSet`/`addDropSet`/`updateSet` (`setSeedSchema`/`updateSetPatchSchema`), `completeSet` (`completeSetValuesSchema`), `setExerciseNote`/`setSessionNotes` (`nullableNoteSchema`, `.trim().max(WORKOUT_NOTE_MAX_LENGTH)`), `startEmpty`'s title (`titleSchema`), `setSupersetGroup`'s group (`supersetGroupSchema`), and both start methods' `startedAt` (`timestampSchema`). Schemas map directly to the DB's own `CHECK` constraints (`reps BETWEEN 0 AND 1000`, `rpe BETWEEN 1 AND 10`, `weight_kg >= 0`) rather than inventing separate bounds - a validation gap can't silently diverge from what SQL would reject anyway.

`stores/activeWorkoutStore.ts` was read in full: every action is a pure local-state reducer (`set()` calls only) with no SQL, no `fetch`, no direct repository import - it cannot become a second unvalidated write path, because it never writes to persistence at all. All 12 mutation hooks in `hooks/{useSetMutations,useExerciseMutations,useNotes}.ts` follow the documented ADR-0008 pattern: synchronous store update (or await-then-commit for non-hot-path edits) plus a `sessionService.*` call, reconciling from `sessionService.findInProgress()` on failure (`hooks/sessionSync.ts`) - never a store mutation alone.

One inconsistency, not a vulnerability (see Findings SEC-002): `saveActiveState` has no Zod schema in the service - it passes `ActiveStatePatch` straight through. Not exploitable: the type only carries `sessionId`/`focusedSessionExerciseId` (both ids) and `scrollOffset` (a number), all bound as SQL parameters regardless, with no free-text field and no CHECK constraint they could violate.

### 3. Transaction correctness / atomicity - PASS
Every multi-statement repository method follows the same `tx ? runner(tx) : this.deps.db.transaction(runner)` composition already verified for `SqlitePlanRepository` in the P5 report, so calling any of them standalone wraps its statements in one transaction and calling them with a caller-supplied `tx` joins that outer transaction.

- `startFromPlanDay`'s loop inserting one `session_exercise` row per plan-day exercise runs inside the same transaction as the session-row insert and the in-progress pre-check - a crash mid-loop rolls back the whole start, never leaving a partial exercise list.
- `finish()`'s read (sum sets), compute (`computeSessionTotals`), and write (denormalized totals + `active_session_state` delete) happen inside one transaction - no window where `total_volume_kg` could be written without `active_session_state` also being cleared, or vice versa.
- `insertSession`'s own try/catch around the unique-constraint violation (`ux_session_single_in_progress`) is inside the same transaction as the row insert it's guarding, so a raced double-start either commits the first writer's session and cleanly rolls back the second's partial insert, or (pre-checked by `assertNoSessionInProgress`) never attempts the second insert at all.
- `removeExercise`/`deleteSet`'s two-statement cascade (soft-delete the parent row, then its children) and `restoreExercise`/`restoreSet`'s matching restore both run inside one transaction each - no window where an exercise is marked deleted but its sets are not, or vice versa.
- `reorderExercises`'s per-id loop of `UPDATE`s runs inside one transaction with a not-found check (`result.changes === 0`) per iteration - a bad id aborts the whole reorder rather than leaving sort orders half-renumbered.

### 4. Soft-delete / `deleted_at IS NULL` filter coverage - PASS (one LOW note)
Checked every `SELECT`/`UPDATE` in the file:
- `findInProgress`, `loadAggregate`'s exercise/set queries, `loadSessionExercise`, `addExercise`'s count/shift queries, `removeExercise`/`restoreExercise`/`deleteSet`/`restoreSet`'s guard reads, `appendSet`/`addDropSet`/`updateSet`/`completeSet`/`uncompleteSet`'s guard reads, and every `updateRowIn` call (which filters `deleted_at IS NULL` in its own `WHERE` internally) all correctly exclude soft-deleted rows from a result the UI trusts.
- **`findInProgressId`** (used by `assertNoSessionInProgress` and the service's blocked-session path) deliberately omits `deleted_at IS NULL` - correct per its own doc comment: `ux_session_single_in_progress` has no soft-delete predicate either, so a soft-deleted in-progress row must still be reported as the blocker it is at the database level.
- **`loadExerciseSummaries`** deliberately omits `e.deleted_at IS NULL` on the `exercise` join, same reasoning and same acceptable pattern the P4/P5 reports already verified for this exact query shape (a referenced exercise can't be hard-deleted, and `ExerciseService`'s delete guard prevents soft-deleting one still referenced by an active plan/session in the intended flow).
- **`setSupersetGroup`'s final `UPDATE ... WHERE id IN (${placeholders})`** (line 679) has no `deleted_at IS NULL` filter, mirroring the identical, already-accepted LOW finding in the P5 report for `SqlitePlanRepository.setSupersetGroup`. Not exploitable here either - the ids were verified non-deleted by the same-transaction membership `SELECT` a few lines above, and this is a single-user, single-writer, offline app with no concurrent client that could soft-delete a row between the two statements inside one exclusive transaction. See SEC-001.

## Findings

### [SEC-001] `setSupersetGroup`'s final `UPDATE` omits `deleted_at IS NULL` - LOW
**Category**: Local data integrity / defense-in-depth
**Location**: `features/workout-logging/repository/SqliteWorkoutSessionRepository.ts:678-681`
**Reproduction**: Not reachable today - the ids are verified non-deleted by the same-transaction membership `SELECT` (lines 664-667) a few lines above, and this app has no concurrent writer that could soft-delete one of those `session_exercise` rows inside that same exclusive transaction.
**Impact**: None under the current single-user, single-writer execution model. Purely a consistency gap versus every other write in this file (`updateRowIn`, `reorderExercises`'s `UPDATE`) which do filter on it.
**Fix**: Add `AND deleted_at IS NULL` to the `UPDATE session_exercise SET superset_group = ? ... WHERE id IN (...)` statement, for consistency - optional, not a release blocker. (Same finding, same disposition, as the P5 report's note on `SqlitePlanRepository.setSupersetGroup`.)

### [SEC-002] `saveActiveState` has no Zod schema in the service layer - LOW
**Category**: Input validation boundary / consistency
**Location**: `features/workout-logging/services/WorkoutSessionService.ts:259-261`
**Reproduction**: `sessionService.saveActiveState({ sessionId, scrollOffset: Number.MAX_SAFE_INTEGER })` (or any out-of-range number) reaches the repository and is written unchecked to `active_session_state.scroll_offset` (a `REAL` column with no `CHECK` constraint).
**Impact**: None security-relevant - `scrollOffset`/`focusedSessionExerciseId` are UI convenience state (ARCHITECTURE.md section 10.3), not read by any statistic, aggregate, or cross-session logic, and both fields are bound as SQL parameters regardless of value. Worst case is a nonsensical scroll-restore position on next launch, which self-corrects the moment the user scrolls.
**Fix**: Optional, for consistency with every other mutating method on this service: add a small Zod shape (`z.object({ sessionId: entityIdSchema, focusedSessionExerciseId: entityIdSchema.nullish(), scrollOffset: z.number().finite().nullish() })`) and a `check()` call at the top of `saveActiveState`. Not a release blocker.

## Additional notes (informational, not findings)

- **INFO-001**: None of `SetRow.tsx`/`ExerciseHeader.tsx`/`WorkoutHeader.tsx`'s note `TextField`s set a UI-level `maxLength` prop - the 1000-character limit is enforced exclusively at the service/Zod boundary (see checklist item 7), which is the correct place for it to be authoritative, but it means a user who types past the limit only discovers the rejection when the debounced commit fires (`useDebouncedFieldCommit`), which then fails silently into `recoverFromWriteFailure` - the store reconciles from the database (discarding the over-limit edit) and a generic "something went wrong" toast shows, not a specific "note too long" message. This is a UX gap, not a security issue (the persistence-boundary enforcement itself is correct and cannot be bypassed); worth a UI-level `maxLength={WORKOUT_NOTE_MAX_LENGTH}` the next time these components are touched, purely for user feedback quality.
- `WorkoutValidationError`/`SessionAlreadyInProgressError`/`SessionNotInProgressError`/`SupersetSpansMultipleSessionsError`/`DropSetParentInvalidError`/`DropSegmentSetTypeError` messages were checked for information disclosure: every interpolated value is either a static Zod issue message or the app's own internal UUID (session/set/exercise id) - never a stack trace, file path, or raw SQL. In an offline single-user app with no other party to disclose information to, this carries no confidentiality risk; noted only for completeness, consistent with the P5 report's equivalent check.
- `services/container.ts`'s P6 extension (`sessionRepository`/`sessionService` construction and `AppContainer` fields) is a straight repeat of the `planRepository`/`planService` wiring pattern the P5 report already reviewed - same shape, no new composition-root risk.
- `app/(tabs)/_layout.tsx`'s `ActiveWorkoutBanner` mount and `app/(tabs)/index.tsx`'s "Quick Start" button/`PlanDayCard`'s "Start workout" action were reviewed for the same injection/data-exposure surface as the rest of the screen layer and have none - `session.title` and `blockedSession.session.title` render only through `<Text>` or `t()`'s plain-string interpolation, never through anything that parses markup.
