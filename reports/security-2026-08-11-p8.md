## Focus Area Results

### 1. SQL construction in `SqlitePersonalRecordRepository.ts`/`SqliteExerciseHistoryRepository.ts` - PASS
Read both files in full (325 and 218 lines).

- Every `select`/`selectOne`/`run` call across both files binds caller/candidate-derived values (`exerciseId`, `limit`, `recordType`, weights, reps, ids, timestamps) as `?` parameters. No value is ever string-interpolated into SQL text.
- `SqliteExerciseHistoryRepository.ts`'s `RECORD_ELIGIBLE_SET_TYPES_SQL = "('normal', 'failure')"` is interpolated directly into four queries (`getBestPerformance` x3, `listRecentSessionsForExercise`) via template literals, but it is a module-level hardcoded string literal, never built from any argument - the exact "table/clause literal, never caller input" pattern this codebase's own header comments (and the P4-P7 reports) already establish as accepted for `BaseSqliteRepository`'s dynamic table names. No new risk introduced.
- `SqlitePersonalRecordRepository.rebuild()`'s per-exercise loop (`DELETE FROM personal_record WHERE exercise_id = ?` then a parameterized `SELECT ... FROM v_working_set WHERE exercise_id = ?`) binds `exerciseId` from its own just-queried `allCandidateExerciseIds()`/caller-supplied array - never concatenated.
- Neither file does dynamic table-name interpolation at all (unlike `SqliteWorkoutSessionRepository`/`SqlitePlanRepository`'s closed-union table parameter) - both are single-table (`personal_record`) or read-only against one view (`v_working_set`), so that whole risk class doesn't apply here.

**Verdict: no injection surface, no deviation from this codebase's established parameterization discipline.**

### 2. "Recalculate records" bulk action reachability/guard - PASS (one LOW note)
Traced the full path: `SettingsScreen.tsx` row `onPress` -> `setConfirmRebuildVisible(true)` -> `ConfirmDialog` -> `onConfirm` -> `handleConfirmRebuild()` (synchronously closes the dialog, then `await rebuildRecords.mutateAsync()`) -> `useRebuildRecords` (`useMutation({ mutationFn: () => recordService.rebuild() })`) -> `PersonalRecordService.rebuild()` -> `SqlitePersonalRecordRepository.rebuild()`, which opens its own `db.transaction(...)` when called standalone (no `tx` passed from this path) and does a full per-exercise `DELETE` + re-walk of `v_working_set`.

- **Re-entry from the Settings list is correctly blocked**: the `ListRow` itself is `disabled={rebuildRecords.isPending}` and shows a spinner, so once the mutation is genuinely in flight (React Query's `isPending` has flipped), a second tap on the row cannot reopen the confirm dialog.
- **The remaining gap is a double-tap on the `ConfirmDialog`'s own Confirm button**, in the narrow window between the tap and the `isPending` state propagating: `ConfirmDialog` (`components/feedback/ConfirmDialog.tsx`) takes no `loading`/`disabled` prop and its Confirm `Button` is never disabled while `handleConfirmRebuild` is running, so two touch events landing on it before the modal actually unmounts could both call `mutateAsync()`, starting two overlapping `rebuild()` transactions.
- **This is not a P8-introduced pattern** - it is byte-for-byte the same shape already used throughout this codebase (e.g. `PlanListScreen.handleConfirmDelete`: `setDeleteTarget(null)` then `await deletePlan.mutateAsync(target.id)`, same unguarded `ConfirmDialog` Confirm button), so P8 does not lower the bar - it just attaches this same pre-existing, already-accepted gap to a heavier operation (a full-catalog rewrite instead of one row's soft delete).
- Even if triggered, the underlying transaction primitive (`ExpoSqlExecutor.transaction()` in `database/client.ts`, unchanged by this phase) routes every top-level `transaction()` call through `expo-sqlite`'s `withExclusiveTransactionAsync` against a single connection - the worst realistic outcome of two overlapping calls is serialization/contention (slower, not corrupting), not a lost-update or `ux_pr_current` violation, since each `rebuild()` call is itself a single all-or-nothing transaction.

See LOW-001 below.

### 3. Input validation at the service boundary (`PersonalRecordService`) - PASS
`PersonalRecordService` has no create/update/free-text-input method (unlike `ExerciseService`/`PlanService`, which validate user-authored entities) - every method here is either a pure read (`listCurrent`, `listHistory`) parameterized only by ids that flow straight to a parameterized SQL `WHERE`, or `listRecent(limit)`/`rebuild(exerciseIds)`.

- `listRecent(limit)` runs `limit` through `checkLimit()` -> `z.number().int().min(1).max(500)` before ever reaching the repository, throwing `RecordValidationError` (mirroring `PlanValidationError`/`WorkoutValidationError`'s shape) on an out-of-range or non-integer value - confirmed this is real validation, not a passthrough: `MAX_RECENT_LIMIT = 500` bounds an otherwise-unbounded caller-supplied number before it becomes a SQL `LIMIT ?`.
- `evaluateAndUpsert` (the one method that writes based on external input, a completed set's weight/reps) is deliberately **not** exposed on the service at all - it only runs repository-to-repository from `SqliteWorkoutSessionRepository.completeSet`'s own transaction, which is itself downstream of `WorkoutSessionService.completeSet`'s existing Zod-validated `completeSetValuesSchema` (`reps`/`rpe`/etc. bounds unchanged by this phase). So the actual free-form numeric input this feature evaluates is validated one layer up, at the point it's first accepted from presentation - consistent with the project's existing layering.
- Settings values this feature reads (`oneRm.formula`, `progression.upperIncrementKg`, `progression.lowerIncrementKg`) are Zod-validated on both read and write by `SqliteSettingsRepository` (`entry.schema.safeParse` in both `get`/`set`), confirmed by reading that file - a malformed stored value falls back to schema default rather than reaching a formula calculation unchecked.

**Verdict: validation exists at the correct boundary for every input this feature actually accepts; nothing passes through unchecked.**

### 4. Data integrity under the extended `completeSet` transaction - PASS
Read the diff to `SqliteWorkoutSessionRepository.ts` in full. `completeSet`'s `runner` now calls `this.personalRecordRepository.evaluateAndUpsert(completedSet.exerciseId, candidate, t)` using the **same transaction handle `t`** the rest of `completeSet` already uses (bound via the existing `tx ? runner(tx) : this.deps.db.transaction(runner)` composition) - not a second, independent transaction. A throwing `evaluateAndUpsert` therefore propagates out of `runner` and rolls back the entire `completeSet` transaction, including the earlier `UPDATE workout_set SET is_completed = 1, ...` in the same call.

Independently verified this holds in the actual code, not just via the added test:
- `SqlitePersonalRecordRepository.evaluateAndWrite` (the sole write path both `evaluateAndUpsert` and `rebuild()` use) always uses the passed-in `tx`, never opens its own transaction inside a candidate evaluation - so it genuinely joins the caller's transaction rather than silently committing independently.
- For every beaten record type, it does `UPDATE personal_record SET is_current = 0 ...` (only when a current row exists) followed by one `INSERT ... is_current = 1`, both against the same `tx` - sequential statements inside one transaction, so a crash between them rolls back both, and `ux_pr_current` (`CREATE UNIQUE INDEX ux_pr_current ON personal_record (exercise_id, record_type, IFNULL(rep_bucket, -1)) WHERE is_current = 1`, unchanged from P2) enforces the single-current-row invariant at the SQLite level regardless - the schema already correctly uses `IFNULL(rep_bucket, -1)` so two `NULL`-rep_bucket current rows for the same exercise/record_type can't slip past SQL's normal "NULL != NULL in unique indexes" behavior.
- `evaluateCandidateRecords` (the pure decision function) cannot itself produce two `BeatenRecord` entries with the same `(recordType, repBucket)` key in one call - each of its seven checks targets a distinct `recordType`, and `weight_at_reps` keys on the candidate's own rep-bucket match - so `evaluateAndWrite`'s single up-front `currentRows` read is never invalidated by its own loop.
- Independently re-verified the added regression test (`__tests__/features/workout-logging/repository/SqliteWorkoutSessionRepository.test.ts`, "a throwing personalRecordRepository.evaluateAndUpsert rolls back the entire completeSet transaction") actually exercises this: it injects a real failing `PersonalRecordRepository` implementation (not a mock of the transaction machinery), asserts the rejection propagates, then re-reads `workout_set` from the database and asserts `is_completed`/`completed_at`/`reps`/`rpe` are all back to their pre-`completeSet` values and `personal_record` has zero rows - a genuine integration-level rollback assertion against `NodeSqlExecutor`, not a mocked assertion. This is a real test of the claim, not a rubber stamp.

**Verdict: the rollback guarantee holds in the code, and `ux_pr_current` cannot be violated by any code path in this diff, including a crash mid-write, since every write to `personal_record` happens inside the same transaction that guards `workout_set`.**

## Findings

### [LOW-001] "Recalculate records" confirm button has no in-flight guard of its own - LOW
**Category**: Availability / defensive UI (not injection, not data-integrity)
**Location**: `features/profile/screens/SettingsScreen.tsx:30-38` (`handleConfirmRebuild`), `components/feedback/ConfirmDialog.tsx` (Confirm `Button`, no `disabled`/`loading` prop)
**Reproduction**: Tap the "Recalculate records" row to open the confirm dialog, then double-tap the dialog's Confirm button quickly enough that both touches register before the modal closes (a fast, deliberate double-tap; not triggerable by a single normal tap).
**Impact**: Two `PersonalRecordService.rebuild()` calls could start close together, each opening its own `db.transaction()`. Given `ExpoSqlExecutor.transaction()`'s single-connection `withExclusiveTransactionAsync` serialization (unchanged infrastructure, not part of this diff), the realistic worst case is redundant work/slower completion, not data corruption - `rebuild()` itself is idempotent (it always fully regenerates the target exercise's records from `v_working_set` inside one all-or-nothing transaction) and `ux_pr_current` backstops the invariant regardless. Same theoretical gap already exists, unaddressed, on every other `ConfirmDialog`-gated mutation in this codebase (e.g. `PlanListScreen`'s delete-plan flow) - P8 does not introduce a new class of risk, only a heavier operation behind the existing pattern.
**Fix**: Optional. If ever hardened, the natural fix is adding an `isConfirming`/`loading` prop to `ConfirmDialog` itself (disabling its own Confirm button once pressed) rather than a per-screen workaround - that would close this gap for every caller at once, not just this one. Not a release blocker; consistent with how the P5/P6 reports treated equivalent low-severity, pre-existing-pattern findings.

## Additional notes (informational, not findings)

- **INFO-001**: `SqlitePersonalRecordRepository` and `SqliteExerciseHistoryRepository` both deliberately do not extend `BaseSqliteRepository` (documented in each file's own header comment: `personal_record` has no `deleted_at` column by ADR-0015 design, and the history repository is read-only). This is an architectural deviation, not a security gap - confirmed both files still route every value through parameterized queries independent of that base class, so none of `BaseSqliteRepository`'s injection-safety guarantees are actually lost by opting out of it.
- `services/container.ts`'s P8 extension (`recordRepository`/`recordService`/`exerciseHistoryRepository` construction, and threading `recordRepository` into `SqliteWorkoutSessionRepository`'s new fourth constructor dependency) is a straight repeat of the composition-root wiring pattern the P5/P6/P7 reports already reviewed for `planRepository`/`sessionRepository` - no new composition-root risk.
- No new npm dependency: `git diff main -- package.json package-lock.json` is empty.
- No `database/schema.sql` change in this diff - `personal_record` and `ux_pr_current` are unchanged P2 schema, confirmed by reading the relevant section directly rather than trusting the phase description.
- `exerciseHistoryRepository`/`recordService` are passed from `app/(tabs)/exercises/[id].tsx` and `SessionExerciseCard.tsx` down into feature hooks via `useContainer()`, rather than those hooks calling `useContainer()` internally - documented in both files as a deliberate cycle-avoidance choice (the hooks live in barrels the container itself imports from). This is an architecture-layering consideration, not a security one; no direct SQL or unvalidated write path reaches presentation as a result.
