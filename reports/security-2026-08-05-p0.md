## Findings

### [SEC-001] Transitive `uuid` advisory (GHSA-w5hq-g745-h8pq) not caught by the `--audit-level=high` gate - LOW
**Category**: Dependency & Supply Chain
**Location**: `package-lock.json` - `expo-splash-screen@57.0.5` -> `@expo/config-plugins@57.0.6` -> `xcode@3.0.1` -> `uuid@7.0.3`
**Reproduction**: `npm audit --json` reports 11 moderate advisories, all resolving to the same root cause: `xcode@3.0.1` pins `uuid@7.0.3`, which is affected by a missing buffer bounds check in `uuid.v3/v5/v6` when a caller-supplied `buf` argument is used (CWE-787/CWE-1285). npm's own severity label is "moderate", but the underlying CVSS score is 7.5 (`AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:H/A:N`) - solidly in "high" territory on the raw CVSS scale, it just isn't classified that way in the GitHub Advisory Database entry npm ingests. `audit:ci` (`npm audit --audit-level=high`) therefore passes cleanly and this never appears as a CI failure.
**Impact**: In practice this is not exploitable in this app. `xcode` is a build-time tool that `@expo/config-plugins` uses to edit native Xcode project files during `expo prebuild`/EAS builds - it never ships inside the app bundle and never runs against untrusted input at runtime. The advisory only matters if code calls `uuid.v3/v5/v6(name, namespace, buf, offset)` with an undersized `buf`; nothing in this dependency chain does that. Flagging this because the user asked not to blindly trust the `--audit-level=high` cutoff for what's meant to become a real production app - it's worth having on record, but it is not a runtime risk today.
**Fix**: No action needed now. `npm audit`'s suggested fix (`expo@46.0.21`, a major downgrade) is not viable and would be worse than the advisory itself. Re-check `npm ls uuid` next time `expo-splash-screen`/`@expo/config-plugins` gets a minor/patch bump - Expo SDK updates periodically bump `xcode` and typically resolve this on their own. Revisit if `audit:ci`'s severity gate is ever loosened or if `uuid` ever becomes a direct/runtime dependency.

### [SEC-002] GitHub Actions pinned to major-version tags, not to a commit SHA - LOW
**Category**: CI/CD Pipeline Security / Supply Chain
**Location**: `.github/workflows/ci.yml:39-41,87`
**Reproduction**: `uses: actions/checkout@v7`, `uses: actions/setup-node@v7`, `uses: actions/upload-artifact@v7` all reference a mutable major-version tag rather than a full commit SHA (`actions/checkout@<40-char-sha> # v7`).
**Impact**: All three actions are first-party GitHub Actions (`actions/*`), which is the lowest-risk category of third-party Action to depend on, so exploitability here is low. The residual risk is standard Action-tag supply-chain exposure: a tag can be force-moved (by GitHub or, in a compromise scenario, by an attacker with push access to the `actions/*` org) to point at different code than what was reviewed, and the workflow would silently pick up the new commit on the next run with no diff for anyone to review. This is a routine hygiene item, not a live threat given the low-privilege `permissions: contents: read` block already in place and the absence of any secrets in this workflow.
**Fix**: Optional hardening, not blocking: pin each `uses:` to a commit SHA with the version as a trailing comment (e.g. `actions/checkout@<sha> # v7`) and let Dependabot/Renovate bump the SHA on a schedule. Given this is a solo-developer, no-secrets CI job today, this is a "nice to have before the pipeline touches anything sensitive" item rather than something to fix immediately.

### [SEC-003] EAS `submit.production` block is empty - informational, verify before first store submission - LOW
**Category**: EAS/Mobile Release Config
**Location**: `eas.json:38-40`
**Reproduction**: `"submit": { "production": {} }` - no `serviceAccountKeyPath` (Android) or `appleId`/`ascAppId` (iOS) configured.
**Impact**: Not a vulnerability - there's nothing to leak because nothing is configured yet, and an empty submit profile can't accidentally expose credentials. Noting it only because when this does get filled in (App Store Connect API key path, Google Play service account JSON path), those key files must stay outside the repo and covered by `.gitignore`, and any inline secret values EAS supports (`ascApiKeyPath`, etc.) should go through `eas secret` / environment variables, never committed inline in `eas.json`. `.gitignore` already covers `*.p8`, `*.p12`, `*.jks`, `*.mobileprovision`, and `.eas/`, which is the right groundwork for this.
**Fix**: No action now. When `submit.production` is filled in during a later phase, re-verify the credential file paths it references are git-ignored and that no key material lands directly in `eas.json`.
