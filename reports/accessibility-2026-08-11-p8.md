## Summary

## Findings

### [A11Y-P8-001] `PRBadge` renders inside `SetRow`'s pre-existing `SwipeableRow`-collapsed container and is not independently reachable or announced - **BLOCKING**, REPORT ONLY
**Category**: Gesture accessibility / operable, perceivable - the exact bug class CLAUDE.md's "Known gaps" and two prior audits track for this codebase
**Location**: `features/workout-logging/components/SetRow.tsx:97-104` (the outer `View` that is `SwipeableRow`'s single `children`), combined with `components/gestures/SwipeableRow.tsx:154-171,239-258` (`attachAccessibilityActions`)

**The mechanism**: `SetRow` always supplies both a `leftAction` (delete) and a `rightAction` (edit) to `SwipeableRow` (lines 80-91), so `hasActions` is always `true`. `SetRow`'s entire visible body - the `Row` containing the set-number `PressScale`, the weight/reps `NumberField`s, the completion `Checkbox`, the new P8 `PRBadge` block, and (when expanded) the set-type `Chip`s, RPE field, note field, and "add drop set" chip - is one single `<View>` (line 99), passed to `SwipeableRow` as its one `children` element. Because `children` is a single valid element, `SwipeableRow`'s `canAttachToChild` branch fires: `attachAccessibilityActions` clones `accessible: childProps.accessible ?? true` plus the swipe `accessibilityActions`/`onAccessibilityAction` directly onto that outer `View`. `SwipeableRow`'s own doc comment (lines 134-147) explicitly anticipates this cloning target being "something with its own primary interaction (e.g. a pressable `ListRow`)" - a single control. `SetRow` hands it a compound container with five-plus independent controls instead, which is precisely the shape the comment doesn't cover.

**Empirical proof** (not just static reading): a throwaway RNTL test mounted the real `SetRow` with `prRecords` non-empty (the exact prop `SessionExerciseCard.tsx:138-139` passes for a set that just earned a PR) and dumped every node carrying an accessibility-relevant prop:

```
[View] root :: testID=set-row
  [View] root>2>0 :: accessible=true, actions=[{"name":"leftAction","label":"Delete set"},{"name":"rightAction","label":"Edit set"}]
    [View] root>2>0>0>0 :: accessible=true, role=button, label=Set 1, Normal
    [TextInput] root>2>0>0>1>0 :: label=Weight, testID=set-row-weight
    [TextInput] root>2>0>0>2>0 :: label=Reps, testID=set-row-reps
    [View] root>2>0>0>3>0 :: accessible=true, role=checkbox, label=Mark set 1 complete, testID=set-row-complete
    [View] root>2>0>1>0 :: role=text, testID=set-row-pr-badge
```

`root>2>0` is the cloned outer `View` - it alone carries the swipe `accessibilityActions`, confirming the clone landed exactly where the code trace predicts. Every other accessibility-bearing node in the row - the set-number button, the checkbox, and `PRBadge`'s own node - is a *descendant* of that already-`accessible=true` node, not a sibling of it. `PRBadge`'s node (`root>2>0>1>0`) doesn't even carry `accessible=true` on its own (see A11Y-P8-002) - so even setting the ancestor-collapse question aside, there is no path by which VoiceOver/TalkBack would land on it as a distinct, independently-announced stop. It becomes, at best, un-surfaced text folded into whatever the ancestor's merged announcement ends up being; at worst, per the same collapse behavior this codebase's own `SwipeableRow.tsx` comment (lines 136-139) and `DraggableList.tsx`'s consumer-side finding (A11Y-P5-001) describe, it and the checkbox/number-field/focus-button nodes nested beside it never register as separate accessibility elements at all.

**Why this predates P8 but still blocks P8**: `git diff main -- features/workout-logging/components/SetRow.tsx` shows P8's only edit to this file is adding the `prRecords` prop and the `PRBadge` render block (14 lines) - the outer collapsing `View` and its always-on `leftAction`/`rightAction` pair were already there from P6. This audit is not asserting P8 introduced the collapse mechanism. It is asserting that P8's own new UI - the thing this audit was explicitly asked to check ("confirm it doesn't collapse into `SetRow`'s existing accessible container ... a badge that silently swallows focus or duplicates announcement is not [fine]") - fails that check, empirically, not hypothetically. The task's own stated bar makes this the gating finding for this phase's commit, independent of blame for the underlying container.

**Not confirmed, flagged as plausible but device-unverified** (same epistemic caveat A11Y-004/A11Y-P5-002 used): whether the nested `accessible=true` `Checkbox`/`PressScale` nodes are *fully* unreachable on a real iOS/Android device, versus merely folded into a confusing merged label, cannot be settled by RNTL's prop-tree inspection - it doesn't simulate the native accessibility engine's subtree-collapsing behavior. The two `TextInput` nodes (weight/reps) are a separate, more OS-favorable case: native text inputs are typically kept independently focusable by both VoiceOver and TalkBack even under an `accessible=true` ancestor, because text entry requires real keyboard focus - this is a genuine platform nuance, not confirmed or denied here.

**Why this isn't a small fix**: the same conclusion A11Y-P5-001 reached applies here. `SetRow`'s outer `View` needs to stop being the thing `SwipeableRow` attaches its actions to, or `SetRow` needs restructuring so its interactive controls (and `PRBadge`) sit outside that single collapsed subtree - the same "split the row so only the intended primary/swipe target carries the collapsed node" pattern P7's write-up used to fix `RestTimerBar`'s equivalent bug (CLAUDE.md's P7 section: "restructuring so `SwipeableRow` wraps only the countdown `PressScale` ... with the two adjust buttons rendered as independent siblings"). `SetRow` has no single "primary interaction" the way `RestTimerBar`'s countdown `PressScale` was - its whole point is exposing several independently-operable controls per row - so the fix is a real design decision (which control, if any, becomes the swipe-attachable primary target; everything else moves outside `SwipeableRow`'s child), not a one-line prop change. Reporting rather than fixing directly, per this audit's read-only scope.

### [A11Y-P8-002] `PRBadge`'s `accessibilityRole="text"` has no paired `accessible` prop, so the role is inert - LOW, informational, inherited pattern
**Category**: Roles/labels
**Location**: `features/records/components/PRBadge.tsx:55-68`

`PRBadge`'s outer `View` sets `accessibilityRole="text"` but never sets `accessible`. This codebase already documents, in its own source, why that's a no-op: `components/ui/SegmentedControl.tsx:36-44`'s comment states plainly, "A plain `View` defaults `accessible` to `false`, so without this the `tablist` role above is invisible to both RNTL and real screen readers ... they skip any host element that isn't itself opted in via `accessible`" - and the dev-only `app/dev/db-health.tsx` (lines 249, 280) shows the correct paired form (`accessible accessibilityRole="text" accessibilityLabel={...}`) elsewhere in this same codebase. `PRBadge` instead mirrors `components/ui/Badge.tsx`'s existing primitive (`accessibilityRole="text"` with no `accessible`, line 44) - so this is a copied pre-existing pattern from an already-shipped P1 primitive, not a novel mistake, and its practical impact is muted because the inner `Text` node is natively accessible on its own (RN gives `Text` elements accessibility by default without needing an explicit `accessible` prop) - the badge's "New PR!" text would likely still surface as a bare text stop even with the role inert. What's lost is the intended grouping semantic (icon + text read as one labeled unit rather than a bare, unlabeled text fragment next to a silent icon glyph). Given A11Y-P8-001 already places this node inside a fully collapsed ancestor, this finding is largely moot in the current tree, but is worth fixing independently of that one (a one-prop change, `accessible` added to both `PRBadge.tsx` and, out of this phase's scope but worth a follow-up, `Badge.tsx` itself) since it would matter the moment A11Y-P8-001 is resolved and `PRBadge` becomes reachable on its own.

### [A11Y-P8-003] `PersonalRecordsScreen`'s loading/empty/error states are never announced to screen readers - HIGH, REPORT ONLY
**Category**: Perceivable / transient content - an explicit item in this project's own Definition of Done
**Location**: `features/records/screens/PersonalRecordsScreen.tsx` (entire file - no `AccessibilityInfo` import, no announcement call anywhere)

`PersonalRecordsScreen` swaps between a `RecordsListSkeleton`, an `ErrorState`, an `EmptyState`, and the real `FlashList` purely by conditional render, with zero `AccessibilityInfo.announceForAccessibility()` call anywhere in the file. This is a clear, checkable violation on three separate axes:

1. **`Skeleton.tsx`'s own documented contract is violated.** Its doc comment states explicitly: "Hidden from screen readers entirely: a loading skeleton has no meaningful content to announce, and the loading state itself is communicated at the screen level (e.g. an `accessibilityLiveRegion` 'Loading' announcement from the containing view), **not per-skeleton**." `PersonalRecordsScreen`'s `RecordsListSkeleton` renders five bare `Skeleton` components and nothing at the screen level picks up the announcement obligation `Skeleton` explicitly hands off.
2. **Its own sibling screen in this exact phase does it correctly.** `features/profile/screens/ProgressionSettingsScreen.tsx:47-51` (also new in P8) has: `useEffect(() => { if (showSkeleton) { AccessibilityInfo.announceForAccessibility(t('common.loading')); } }, [showSkeleton]);` - the identical pattern `features/profile/screens/UnitsSettingsScreen.tsx:41-44` and `features/profile/screens/ProfileScreen.tsx:20-24` already established. `PersonalRecordsScreen` is the one new P8 screen that doesn't follow it, not because the pattern is unknown to this phase's own diff, but inconsistently applied within it.
3. **It's a codebase-wide convention with 7+ existing adopters.** `grep -rl announceForAccessibility features/ app/` finds it in `PlanDayEditorScreen.tsx`, `ProgressionSettingsScreen.tsx`, `UnitsSettingsScreen.tsx`, `ProfileScreen.tsx`, `ExerciseLibraryScreen.tsx`, `ExerciseDetailScreen.tsx`, `ExercisePickerScreen.tsx`, `OnboardingScreen.tsx`, and the dev-only `db-health.tsx`.

Net effect: a VoiceOver/TalkBack user opening "Personal records" with zero PRs (a real, expected first-run state per this phase's own edge-case list) hears nothing proactive when the screen resolves from "loading" to "no records yet" - they'd have to blindly explore the screen to discover the empty state exists, exactly the "silently swapped in" failure mode the task brief named. Same gap applies to the error state and, less severely, the successful-load transition (though a non-empty list arguably self-announces via normal swipe navigation once explored, unlike the two silent terminal states).

### [A11Y-P8-004] `SettingsScreen`'s "Recalculate records" pending state has no `busy` accessibility state and its `ActivityIndicator` has no label - MEDIUM, REPORT ONLY
**Category**: Perceivable / transient content
**Location**: `features/profile/screens/SettingsScreen.tsx:71-82`, `components/ui/ListRow.tsx:76-79`

The "Recalculate records" row is a `ListRow` with `disabled={rebuildRecords.isPending}` and a bare `<ActivityIndicator color={color.textTertiary} />` passed as `trailing` while pending. Tracing this through:

- `ListRow.tsx:76-79` forwards `disabled` into `accessibilityState={{ disabled }}` on the row's `PressScale` - correct as far as it goes, so a VoiceOver/TalkBack user would hear the row as unavailable while the recompute runs.
- But `ListRow` has no `busy`/`loading` concept at all - unlike `components/ui/Button.tsx:126-132`, which sets `accessibilityState={{ disabled: isDisabled, busy: loading }}` and swaps its label region for a labeled `ActivityIndicator` region specifically to solve this exact problem elsewhere in the same design system. `SettingsScreen.tsx` reaches for `ListRow` + a raw `ActivityIndicator` instead of `Button`'s already-solved `loading` prop, so the `busy` semantic never gets set here.
- The bare `<ActivityIndicator>` itself carries no `accessibilityLabel` - a sighted user sees it spin; a screen-reader user gets nothing indicating *why* the row just became unavailable.
- `subtitle` (`t('records.recalculate.rowSubtitle')`, "Rebuild personal records from your workout history") is a static string that does not change while the mutation is in flight - so the row's full spoken label (`ListRow.tsx:78`: `${title}, ${subtitle}`) stays "Recalculate records, Rebuild personal records from your workout history" throughout, with only the terse `disabled`-state addition ("dimmed"/"unavailable", platform-dependent wording) hinting anything changed - no explicit "in progress" or "recalculating" wording ever reaches the user.

A screen-reader user tapping this row hears the tap register, then has no confirmation an operation actually started until the `ConfirmDialog`'s own confirm button interaction completes and (eventually) the success/error `Toast` fires - which, per this codebase's existing A11Y-002 fix, is itself announced correctly once it appears, so the *end* of the operation is perceivable; only the *in-progress* window is silent.

## Confirmed correct (checked explicitly, no defect found)

- **`ProgressionHint`'s apply affordance** (`features/records/components/ProgressionHint.tsx`): the tap-to-apply element uses a real `PressScale` with `accessibilityRole="button"` and a label that states the concrete action - `t('records.progressionHint.applyAccessibilityLabelTemplate', { weight, reps })` renders as "Apply suggested {{weight}} kilograms for {{reps}} reps" (`i18n/catalogs/en.ts`), not a bare "Apply." When `onApply` is `undefined` (no next incomplete set, per this phase's own documented rule in `SessionExerciseCard.tsx:89-103`), the component renders a plain, non-interactive `View` wrapping the same content with no `PressScale` and no `onPress` - nothing dead, disabled-but-focusable, or silently no-op is left behind, exactly matching this phase's own brief. The `first_time` variant and the `suggestion === null` (renders nothing) variant were both read and are correctly non-interactive/absent respectively.
- **`PersonalRecordsScreen`'s `FlashList` wiring** (`features/records/screens/PersonalRecordsScreen.tsx:72-86`): real `data`/`keyExtractor`/`renderItem` props, matching `ExerciseLibraryScreen.tsx`'s established usage; `@shopify/flash-list` is pinned at `2.0.2` in `package.json`, which does not require `estimatedItemSize`. Confirmed actually wired, not just imported and unused.
- **`ProgressionSettingsScreen`'s formula selector and increment fields** (`features/profile/screens/ProgressionSettingsScreen.tsx`): `SegmentedControl` (`components/ui/SegmentedControl.tsx`) already exposes `accessibilityRole="tab"` + `accessibilityState={{ selected }}` per segment and `accessibilityRole="tablist"` + `accessible` on the group container - correctly consumed here with no deviation from `UnitsSettingsScreen.tsx`'s precedent. The two `StepperField`s get specific, non-generic accessibility labels via `i18n/catalogs/en.ts`: `progressionSettings.upperIncrementAccessibilityLabel` = "Upper body increment, kilograms" and `lowerIncrementAccessibilityLabel` = "Lower body increment, kilograms" - not the generic "Increment" the task brief was checking against. The screen's own top-level loading state *does* announce correctly (`useEffect` + `AccessibilityInfo.announceForAccessibility(t('common.loading'))`, lines 47-51) - this is the screen that got the pattern right; contrast with A11Y-P8-003.
- **Color-only signaling**: both `PRBadge` (trophy `Ionicons` + `t('records.badge.label')` text + `color.accentSubtle`/`color.accentText`) and `ProgressionHint` (`trending-up-outline` `Ionicons` + text + `color.accentText`) pair their accent color with both an icon and text on every rendered branch - never color alone.
- **`ConfirmDialog`** (`components/feedback/ConfirmDialog.tsx`), reused unchanged by `SettingsScreen.tsx`'s new "Recalculate records" flow: `accessibilityViewIsModal` is correctly paired with `accessible={false}` on the same content container (the pattern P1's A11Y-006 already confirmed correct), so title/message/Cancel/Recalculate stay independently reachable inside the isolated modal subtree. No new defect introduced by this phase's usage of it.
- **`ExerciseDetailScreen`'s two new slots** (`previousPerformanceSlot`/`personalRecordsSlot`) and their host-route fillers in `app/(tabs)/exercises/[id].tsx`: structurally sound slot pattern, correct empty-state fallback via `PerformanceEmptySection` when no slot content is supplied (preserves `exercise-library`'s dependency-free-leaf rule). Their own per-slot `isPending` states use bare `Skeleton`s with no screen-level announcement addition for the slot transition specifically - this mirrors the pre-existing, already-shipped (P4) top-level `ExerciseDetailScreen` `isPending` gate, which likewise has no announcement of its own. Noting this for completeness rather than as a new finding: it's consistent with this screen's existing, unaudited-until-now local convention rather than a new deviation P8 introduced, and the two new sections are secondary content within an already-loaded screen rather than the screen's sole content the way `PersonalRecordsScreen`'s states are.

## Recommendations, priority order

1. **Blocking, before this phase can be considered to satisfy its own accessibility bar for `PRBadge`**: resolve A11Y-P8-001. This requires deciding how `SetRow`'s multiple independent controls (focus button, weight field, reps field, checkbox, `PRBadge`, and the expanded-state controls) should relate to `SwipeableRow`'s single-child-attachment contract - at minimum, stop attaching `SwipeableRow`'s cloned `accessible`/`accessibilityActions` to the same `View` that also contains `PRBadge` and the row's other controls. The concrete shape of the fix (which single element becomes the swipe-actions target; everything else rendered as an accessible sibling outside that subtree) is a real design decision for `SetRow`'s consuming team, not a one-line patch - matching how P7's write-up describes the equivalent `RestTimerBar` fix as a restructuring, not a prop tweak.
2. **Recommended alongside #1, small and mechanical**: add `accessible` to `PRBadge.tsx`'s outer `View` (A11Y-P8-002) so its `accessibilityRole="text"` actually takes effect once it's no longer nested inside a foreign collapsed container; consider the same one-line fix for `components/ui/Badge.tsx` as a follow-up, since it's the primitive `PRBadge` copied the flaw from.
3. **Before this phase ships, non-blocking but a clear regression from this phase's own established pattern**: add the `useEffect` + `AccessibilityInfo.announceForAccessibility(t('common.loading'))` pattern to `PersonalRecordsScreen.tsx` for its `isPending`/`isError`/empty transitions (A11Y-P8-003), copying `ProgressionSettingsScreen.tsx`'s own same-phase implementation almost verbatim.
4. **Non-blocking, small**: give the "Recalculate records" row a `busy` accessibility state and a labeled or announced in-progress signal (A11Y-P8-004) - either move it onto `Button`'s existing `loading` prop (which already solves this) or add an equivalent `accessibilityState={{ busy: rebuildRecords.isPending }}` plus a one-time `AccessibilityInfo.announceForAccessibility` when the mutation starts.
5. **Not scoped to this phase, flagged for awareness**: A11Y-P8-001's root cause - `SwipeableRow` collapsing a multi-control child into one node when it's handed something other than a single-interaction element - is very likely present in every other `SwipeableRow` consumer that wraps more than one control (not audited here beyond `SetRow`, since it's the only P8-touched one). Worth its own follow-up sweep across the codebase's other `SwipeableRow` usages, tracked the way CLAUDE.md's "Known gaps" section tracks the equivalent `DraggableList` history.

## Sign-off

This audit does **not** clear P8 to commit as-is with respect to `PRBadge`'s accessibility bar. `ProgressionHint`, `PersonalRecordsScreen`'s list wiring, and `ProgressionSettingsScreen` are all correctly implemented and need no changes. `PersonalRecordsScreen`'s missing state announcements (A11Y-P8-003) and the "Recalculate records" row's missing busy signal (A11Y-P8-004) are real, non-blocking gaps worth closing before ship but do not gate this commit on their own. The blocking issue is A11Y-P8-001: empirically confirmed via a real RNTL mount (not just a static read) that `PRBadge` renders inside a `View` that `SwipeableRow` has already marked `accessible={true}` for its own swipe-action purposes - a container inherited from P6, not created by this phase, but one that this phase's own new element lands inside and, per the task's own stated bar, is swallowed by rather than additive to.
