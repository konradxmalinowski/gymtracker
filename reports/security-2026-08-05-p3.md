## Findings

### [SEC-001] `FileStorage.copyFrom()`/`writeText()`/`writeBytes()` do not strip `.`/`..` path segments - LOW
**Category**: Input Validation / Path Traversal
**Location**: `services/files/ExpoFileStorage.ts:8-10` (`pathSegments()`), used by every method that takes a `relativePath`
**Reproduction**: `pathSegments()` splits `relativePath` on `/` and filters only empty segments:
```ts
function pathSegments(relativePath: string): string[] {
  return relativePath.split('/').filter((segment) => segment.length > 0);
}
```
A `relativePath` such as `"../../../Library/secret.txt"` produces segments `['..','..','..','Library','secret.txt']`, passed straight into `new File(this.rootDirectory, ...segments)`. Traced this through `expo-file-system`'s `Paths.join` -> `PathUtilities.join` -> the vendored Node `path.join`/`normalize` (`node_modules/expo-file-system/src/pathUtilities/path.ts`): because the base is an absolute `file://` URI, `normalize()` runs with `allowAboveRoot = false`, so `..` segments only refuse to cross the filesystem root (`/`) - they still walk back up through real segments of the app's own sandboxed path (e.g. out of `Documents/` into a sibling directory under the app container such as `Library/` or `tmp/`). This is not a chroot; it's ordinary lexical `..` collapsing.
**Impact**: today, not exploitable - the only caller, `ProfileService.writeAvatar()` (`features/profile/services/ProfileService.ts:103-105`), builds `relativePath` as `` `${AVATAR_DIRECTORY}/avatar-${idGenerator.generate()}.jpg` `` - a fixed constant plus a crypto-random UUIDv7 filename, never user input. But `FileStorage` is documented in its own header as a deliberately generic, shared primitive that later phases (progress photos - P13, JSON export - P9, per `docs/ROADMAP.md`) will call directly, and nothing in the interface or implementation stops a future caller from passing a path built from a stored value or user-influenced string. Worth closing now while there's exactly one caller to update, rather than after a second feature has grown to depend on the current permissive behavior.
**Fix**: in `pathSegments()`, reject or drop any segment equal to `.` or `..` (and reject a `relativePath` that starts with `/` outside the intended base). Minimal version:
```ts
function pathSegments(relativePath: string): string[] {
  const segments = relativePath.split('/').filter((segment) => segment.length > 0);
  if (segments.some((segment) => segment === '.' || segment === '..')) {
    throw new Error(`Invalid relativePath "${relativePath}": traversal segments are not allowed.`);
  }
  return segments;
}
```
Throwing (rather than silently stripping) matches this codebase's existing style of failing loudly on a contract violation (e.g. `ProfileService.writeAvatar`'s own zero-byte-file check).

## Avatar File Handling Review

- **Write-then-commit ordering (ADR-0012)**: confirmed correct in `ProfileService.writeAvatar()` - `files.copyFrom()` is awaited, then `files.size()` is checked to be non-zero, and only after both succeed does the caller (`completeOnboarding`/`updateAvatar`) persist `avatarFileName` to the `user_profile` row. A killed process mid-copy leaves at worst an orphan file with no row pointing at it, never a row pointing at a missing file - matches the ADR's stated invariant.
- **Filenames never derived from user input**: `avatar-${idGenerator.generate()}.jpg` - `idGenerator` is `Uuid7IdGenerator` (`services/id/Uuid7IdGenerator.ts`), which sources randomness from `crypto.getRandomValues`, not `Math.random()`. The nickname (user input) never touches a filename or path anywhere in this diff.
- **Onboarding vs. update failure handling**: `tryWriteAvatar()` swallows a failed avatar write during onboarding (nickname-only profile still created, failure logged via `logging.warn`) while `updateAvatar()` throws on failure - both intentional per the inline comments, and neither path leaks the underlying error to a UI surface beyond `completeOnboarding.isError` rendering a generic, pre-translated message (`onboarding.genericErrorMessage`), not `error.message` directly. No stack trace or file-path disclosure to the user.
- **Path traversal**: see SEC-001 above - not exploitable via any current call path, but the underlying primitive should be hardened.
- **`sourceUri` handling**: `copyFrom(sourceUri, relativePath)` passes `sourceUri` straight into `new File(sourceUri)` with no validation, but `sourceUri` in every current call site is `ImagePicker`'s `launchImageLibraryAsync()` result `asset.uri` - an OS-generated `content://`/`ph://`/`file://` reference, never a user-typed string. Not a finding, but noting it's unvalidated for the record: a future caller that accepts a raw string URI from outside the picker/camera APIs should re-check this.

## Standard Checklist (routine scope)

- **Nickname input validation**: validated twice, consistently - client-side in `OnboardingScreen.tsx`'s `onboardingSchema` (`z.string().trim().min(1).max(NICKNAME_MAX_LENGTH)`) via `@hookform/resolvers/zod`, and again server-side (repository boundary) in `ProfileService.parseNickname()` using the same `NICKNAME_MAX_LENGTH` constant and schema shape. The service-side check is not redundant with the UI check - it's what protects `updateNickname()` and any future non-UI caller. Good defense-in-depth, no bypass path found (both paths funnel through `ProfileService`, which is the only door into the repository per architecture rule 3).
- **SQL injection surface**: `SqliteProfileRepository.ts` - every query uses `?` placeholders (`get`, `create`, `update`), no string concatenation of values into SQL text. `update()`'s dynamic `SET` clause builds *column names* from a fixed, hardcoded set of four known keys (`nickname`, `avatar_file_name`, `birth_date`, `sex`) gated by `patch.<field> !== undefined` checks against a typed `UpdateProfilePatch` interface - never from arbitrary object keys or user-supplied field names, so there's no mass-assignment or column-injection surface either.
- **Settings/profile row corruption resilience**: `haptics.enabled` was added to `SETTINGS_SCHEMA` (`repositories/settings/settingsSchema.ts:35`) as `z.boolean()` with `default: true`, following the same Zod-validated, default-fallback pattern already established for the other 13 settings keys in P2 (not re-architected, just extended). The MMKV mirror (`services/kv/MmkvStore.ts`) independently catches `JSON.parse` failures on a corrupt stored value and returns `undefined` rather than throwing, and `isHapticsEnabled()` (`services/haptics/settings.ts:22`) falls back to `?? true` on that `undefined` - a malformed or missing value degrades to the safe default in both the SQLite path and the synchronous MMKV mirror, never crashes. `user_profile` row corruption: `SqliteProfileRepository` has no separate validation of stored values on read (it trusts the DB shape), but this matches P2's `user_profile` schema design (fixed columns, `NOT NULL` nickname) and is not new risk introduced by this phase - out of scope to re-litigate the schema itself here.
- **Boot sequence (`app/_layout.tsx`)**: reviewed for completeness since it's new in this phase (previously missing entirely). `BootFailureScreen` renders `error.message` on an unhandled boot failure (`t('boot.genericErrorMessage', { detail: boot.message })`) - for an offline, no-backend, no-auth app this carries no credential/token/PII disclosure risk (worst case is a raw SQLite/filesystem error string), so not flagged as a finding, but noted for awareness if a future phase's boot path ever touches something more sensitive.
