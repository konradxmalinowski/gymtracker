## Focus Area Results

### 1. `SqliteCalendarRepository.ts` - full parameterization, no injection surface - PASS

Read both methods in full (`features/calendar/repository/SqliteCalendarRepository.ts:44-70`).

- `monthOverview(year, month, tx?)` builds `localDateFrom` (`${year}-${String(month).padStart(2,'0')}-01`) and `localDateTo` (via `endOfMonth(localDateFrom)`, pure string arithmetic in `features/calendar/domain/localDate.ts`) as plain JS strings, then passes both as bound `?` parameters in the query's own parameter array (`[localDateFrom, localDateTo]`) - never concatenated into the SQL text itself. The query string is a static literal with two `?` placeholders (`WHERE local_date BETWEEN ? AND ?`).
- `yearOverview(year, tx?)` follows the identical shape: `` `${year}-01-01` ``/`` `${year}-12-31` `` are built as JS strings and passed as bound array elements (`[`${year}-01-01`, `${year}-12-31`]`), never interpolated into the SQL text. The query string itself has zero template-literal substitution - `SELECT local_date, SUM(total_volume_kg) AS volume_kg FROM v_session_summary WHERE local_date BETWEEN ? AND ? GROUP BY local_date HAVING SUM(total_volume_kg) > 0 ORDER BY local_date ASC` is a fixed literal.
- Traced this pattern against `SqliteStatisticsRepository.yearlyHeatmap` (`features/statistics/repository/SqliteStatisticsRepository.ts`), which does the exact same `` `${year}-01-01` `` -> bound-array-element construction and passed its own P11 review with zero findings - this is the established, already-reviewed idiom in this codebase, not a novel pattern introduced here.
- Confirmed the binding is real at the execution layer, not just type-safe at compile time: `database/client.ts:50-93` shows `select<T>(sql, params?)` calling `handle.getAllAsync<T>(sql, bindParams(params))` - genuine parameterized execution via Expo SQLite's own bound-statement API, not string formatting. `year`/`month` being typed `number` in TypeScript is irrelevant to this check either way, since neither value is ever placed into the SQL text - only into bound parameter array elements, which are safe regardless of their JS type.

**Verdict: both methods fully parameterized; no template-literal interpolation of `year`/`month` (or any derived date string) into SQL text anywhere in the file; runtime binding is real, not just compile-time type safety.**

### 2. `deleted_at`/`status = 'completed'` filtering consistency with `v_session_summary` - PASS

Read the view definition directly (`database/schema.sql:398-408`), not assumed from its name:

```sql
CREATE VIEW v_session_summary AS
SELECT s.id, s.local_date, s.started_at, s.finished_at, s.duration_seconds,
       s.plan_day_name_snapshot,
       COUNT(DISTINCT vs.session_exercise_id) AS exercise_count,
       COUNT(vs.id)                           AS working_set_count,
       COALESCE(SUM(vs.volume_kg), 0)         AS total_volume_kg,
       COALESCE(SUM(vs.reps), 0)              AS total_reps
FROM workout_session s
LEFT JOIN v_working_set vs ON vs.session_id = s.id
WHERE s.deleted_at IS NULL AND s.status = 'completed'
GROUP BY s.id;
```

Both `monthOverview` and `yearOverview` query `v_session_summary` exclusively - neither queries `workout_session` or `workout_set` directly, confirmed by reading every `FROM`/`JOIN` clause in the file (there are only two queries total, both `FROM v_session_summary` with no join). Since the view itself already bakes in `s.deleted_at IS NULL AND s.status = 'completed'`, and `v_working_set` (joined inside the view, not by this repository) carries its own `deleted_at`/`is_completed` filtering per the P11 report's own confirmation of that view, neither repository method needs to (and correctly does not) redundantly re-filter. A soft-deleted or in-progress/discarded session is correctly absent from every row this repository ever sees - there is no bypass path.

`total_volume_kg` also arrives pre-`COALESCE`d from the view (`COALESCE(SUM(vs.volume_kg), 0)`), matching the class's own header comment - neither method null-coalesces it again, which is correct, not a gap: a session row from `v_session_summary` can never carry a `NULL` `total_volume_kg`.

**Verdict: no redundant re-filtering, no accidental bypass of the view to query the base tables directly, filtering fully inherited and correctly relied upon.**

### 3. `year`/`month` origin - confirmed non-attacker-influenced despite being typed `number` - PASS

Traced the call chain from the UI down to the repository:

- `CalendarScreen.tsx:55-56` derives `year`/`month` via `Number(monthAnchor.slice(0, 4))`/`Number(monthAnchor.slice(5, 7))`, where `monthAnchor` is local component state seeded from `startOfMonth(clock.localDate())` (the injected `Clock`, not a bare `new Date()`) and mutated only via `addMonthsToLocalDate(current, ±1)` (`features/calendar/domain/localDate.ts:75-82`) - pure calendar-arithmetic string manipulation, never parsed from a route param, form field, deep link, or any other external/free-text source. There is no text input or route param feeding `year`/`month` anywhere in this diff (confirmed via `grep -rn "useCalendarMonth\|useCalendarYear" features/calendar` - both call sites are `CalendarScreen.tsx`, both pass this same locally-derived `year`/`month` pair).
- `useCalendarMonth`/`useCalendarYear` (`features/calendar/hooks/`) pass `year`/`month` straight through to the repository with no transformation beyond what's already covered in section 1.
- Even in a hypothetical future caller that fed this an attacker-controlled value, the values only ever reach SQL as bound parameters (section 1) - the injection surface a naive numeric-to-string-interpolation bug would create simply doesn't exist here regardless of the input's trustworthiness.

**Verdict: `year`/`month` are locally-derived calendar-navigation state, not user-facing free text; the runtime SQL binding stays parameterized regardless.**
