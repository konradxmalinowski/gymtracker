## Dependency Audit - New Dependencies (P2 scope)

### `react-native-nitro-modules` (^0.36.5, runtime dependency)

- **Usage confirmed as described**: not imported directly anywhere in app code (`services/kv/MmkvStore.ts` imports only `react-native-mmkv`) - it's `react-native-mmkv@4.3.2`'s native peer, resolved in the tree as `react-native-mmkv -> react-native-nitro-modules@0.36.5 deduped`, confirmed via `npm ls react-native-nitro-modules --all`.
- **Runtime attack surface consideration (the point specifically called out in scope)**: this is a native-module bridge library (JSI/C++ codegen infrastructure - "Nitro Modules"), so unlike a devDependency it does run on-device in the shipped app, not just at build time. Its own code surface is generic JSI/HostObject plumbing shared by every Nitro-based module (also used by `react-native-mmkv`, `react-native-vision-camera`, `react-native-skia` in the broader ecosystem) - it does not itself parse untrusted network input or user-supplied files. The realistic attack surface it introduces is "does the native bridge correctly enforce type/bounds checks across the JS<->native boundary," which is exactly the kind of native-module memory-safety question that's hard to verify from source review alone and is better served by using pinned, released versions (already the case here - `^0.36.5`, matching the version `react-native-mmkv@4.3.2` itself requires) rather than a deep source audit, which would be disproportionate for a routine scope.
- **Provenance**: authored by Marc Rousavy (`mrousavy`), maintainer of `react-native-vision-camera`, `react-native-mmkv`, and a recognized, high-profile contributor to the React Native native-module ecosystem (also a Reanimated/worklets contributor). Repository is `github.com/mrousavy/nitro`, not an anonymous or newly-created account. MIT licensed.
- **Maintenance**: actively released - version 0.36.5 is current at time of audit, matches what `react-native-mmkv@4.3.2` itself declares as its required peer version.
- **Transitive dependencies**: zero. `npm ls react-native-nitro-modules --all` shows no dependencies of its own - the entire risk surface is the package's own JS/C++/Swift/Kotlin source, not a dependency chain. Install footprint is 1.3M on disk.
- **Install lifecycle scripts**: none that execute during this project's `npm install` (see full-lockfile scan above). The package's own `postversion`/`build` scripts run only when the package itself is published by its maintainer, not on consumer install.
- **Known CVEs**: none found for `react-native-nitro-modules` at any version (checked Snyk, Socket.dev, GitHub Advisories, GitLab Advisory Database - all report a clean history for this package).
- **Operational note (not a security finding, flagging for devsecops-agent awareness per the task)**: as stated in the task, this package requires a pod install / prebuild step before the next device run - this is a build-pipeline concern, not a code-level vulnerability, and is out of scope for this report to resolve.

**Assessment**: clean. No CVEs, no install-time code execution, zero transitive dependencies, reputable single-maintainer-but-high-profile provenance. The native, on-device runtime surface is real and worth naming explicitly (unlike `sharp`, this ships in the app bundle) but nothing in the provenance, dependency, or advisory checks raises a concern proportionate to a routine audit.

### `sharp` (^0.35.3, devDependency)

- **Usage confirmed as described**: only call site is `scripts/build-catalog.ts:287` (`sharp(raw)` piped to WebP re-encoding at 512px), a Node script run manually/at build time to regenerate `assets/data/exercises.*.json` and `assets/exercises/*.webp` from the `yuhonas/free-exercise-db` GitHub source. Confirmed via `grep -rln "build-catalog" app/ features/ services/ components/` returning no matches - nothing in app runtime code references this script or imports `sharp`, so it cannot ship in the Metro/Hermes bundle.
- **Attack surface assessment (the point specifically called out in scope)**: `sharp` wraps libvips, which does have a real CVE history for malicious-image-triggered memory corruption (this is exactly the class of bug that matters when a library like this processes untrusted input) - so the "safe because devDependency" assumption was checked, not assumed. Two things narrow this down to non-issue here: (1) it never runs on-device or in the shipped app - it only runs at build time when a developer manually executes `npm run build:catalog`; (2) the image inputs are a fixed, already-vetted upstream dataset (`yuhonas/free-exercise-db`, ~1700 exercise images fetched from a specific pinned GitHub source), not arbitrary user-controlled files - so even the local-attacker "malicious image triggers memory corruption in a build script" scenario requires the attacker to first compromise that specific upstream GitHub repo, which is a supply-chain scenario, not an application vulnerability in this codebase.
- **Known CVEs - checked directly, not assumed absent**: found `GHSA-f88m-g3jw-g9cj` (CVE-2026-33327, CVE-2026-33328, CVE-2026-35590, CVE-2026-35591) - multiple libvips memory-safety/integer-overflow vulnerabilities across TIFF, GIF, and VIPS-format loaders, two rated High (CVSSv4 7.0) via `lovell/sharp`'s own security advisory. **Affected range is sharp versions prior to 0.35.0; fixed in 0.35.0, with 0.35.3 (the version pinned in this project's `package.json` and installed in `node_modules`) shipping libvips 8.18.3.** The installed version is already patched - this is a "checked and clear" result, not an unaddressed finding. It did not surface as an `npm audit` line item, consistent with the installed version already being on the fixed side of the range.
- **Provenance**: `lovell/sharp` (Lovell Fuller), one of the most widely used and long-maintained image-processing packages in the Node ecosystem (multi-million weekly downloads), Apache-2.0 licensed. Not a new or unvetted package.
- **Transitive dependencies**: three direct runtime deps per its own `package.json` - `@img/colour@^1.1.0`, `detect-libc@^2.1.2`, `semver@^7.8.5` - all small, well-known utility packages, plus platform-specific prebuilt binary packages under `optionalDependencies` (23 listed across all OS/arch combinations; only the two relevant to this machine, `@img/sharp-darwin-arm64` and `@img/sharp-libvips-darwin-arm64`, actually installed - `npm ls sharp --all` confirms no other transitive JS dependency chain). Total on-disk footprint for `sharp` + `@img/*`: ~18M, entirely native image-codec binaries, not a sprawling JS dependency tree.
- **Install lifecycle scripts**: none for `sharp` itself or its direct/optional dependencies (see full-lockfile scan above - `sharp` and `@img/*` are not among the four packages with `hasInstallScript`). Platform binaries are selected via npm's standard `optionalDependencies` platform-matching, not a postinstall download/exec step.
- **Known CVEs (transitive)**: `detect-libc` and `semver` at the installed version ranges - none found (npm audit clean for both, no separate advisories on GitHub Advisory Database / OSV.dev at the resolved versions).

**Assessment**: clean at the installed version. The libvips CVE history is real and was worth checking explicitly rather than waving off as "just a build script" - but `sharp@0.35.3` is already past the fix line for the known advisory, and the build-time-only / fixed-upstream-source usage pattern means even a hypothetical future libvips CVE would need a compromised upstream GitHub repo to be exploitable here, not arbitrary user input.

## Recommendations (priority order)

1. No blocking action required before commit - zero CRITICAL/HIGH/MEDIUM/LOW findings against either new dependency.
2. (Informational, no action) The pre-existing moderate `uuid` advisory chain (tracked since P0's SEC-001, restated in P1's SEC-004) is unchanged - still not touched by this phase's dependencies, still deferred to the next Expo SDK bump.
3. (Process note, not a finding) `react-native-nitro-modules` is the project's first Nitro-based native module and its first non-Expo-managed dependency that runs on-device rather than at build time. Worth folding into the same "non-Expo native module" checklist suggested in P1's report (provenance/maintenance/permission checks) so this level of scrutiny is repeatable on future additions like it, rather than re-derived each time.
4. (Operational, hand off to devsecops-agent per the task framing) `react-native-nitro-modules` requires a pod install / prebuild step before the next device run - not a vulnerability, just a build-pipeline dependency to make sure CI/EAS build profiles account for.
5. (Optional, low priority) Since `sharp` and its libvips CVE history is now a known quantity for this project, a version-bump PR touching `sharp` in the future should re-check the current advisory state rather than assuming the pattern established here (build-time-only, fixed upstream source) is timeless - a future change to `build-catalog.ts` that accepts arbitrary/user-supplied image paths would change this risk calculus and should trigger a re-audit.
