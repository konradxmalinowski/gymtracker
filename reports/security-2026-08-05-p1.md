## Dependency Audit - New Dependencies (P1 scope)

### `expo-localization` (~57.0.1)

- **Usage confirmed as described**: only call site is `i18n/locale.ts` (`Localization.getLocales()[0]?.languageTag`), read-only, not wired into any catalog-selection logic yet. Matches the "informational only" framing in the task and the code's own comment referencing decision D-11 (English-only v1).
- **Package management**: Expo-managed native module, in-family with every other Expo SDK package already in the project (`~57.x` pin, matches SDK 57). No version-range anomalies.
- **Maintenance**: latest npm version (57.0.1), published 2026-07-15, tracks the Expo SDK 57 release train directly - actively maintained by the Expo core team, not a community/solo-maintainer package.
- **Transitive dependencies**: exactly one - `rtl-detect@1.1.2` (zero dependencies of its own, small pure-JS RTL/LTR text-direction detection utility). No lifecycle scripts, no known advisories (checked via `npm audit` and OSV.dev - both clean for `expo-localization@57.0.1` and `rtl-detect@1.1.2`).
- **Native surface**: Android `AndroidManifest.xml` contributed by this package is empty - no permissions requested. iOS ships an `PrivacyInfo.xcprivacy` (Apple's required privacy manifest) declaring `NSPrivacyTracking: false`, no collected data types, and exactly one required-reason API category (`NSPrivacyAccessedAPICategoryUserDefaults`, reason `CA92.1` - standard app-group shared-preferences access, a normal Expo-module pattern, not an anomaly). No location, contacts, or other sensitive-permission surface - consistent with "reads the locale tag, nothing else."
- **Known CVEs**: none found (npm audit, OSV.dev) for `expo-localization` or `rtl-detect` at the installed versions.

**Assessment**: clean. Matches its described scope exactly - no permission, dependency, or maintenance concerns.

### `@react-native-community/slider` (5.2.0)

Given the closer look non-Expo-managed native modules warrant (own native build config, no Expo-team maintenance backstop):

- **Usage confirmed as described**: `components/ui/Slider.tsx` is a thin wrapper - `value`/`onValueChange`/`minimumValue`/`maximumValue`/`step`/`disabled`, standard slider API surface, no custom native bridging code added on top of the library. Currently only exercised from `app/dev/gallery.tsx` (the component gallery) - not yet consumed by real feature code, so blast radius today is limited to a dev-only screen.
- **Provenance**: `callstack/react-native-slider` on GitHub - this is the community-designated successor to RN core's removed built-in `Slider` (RN core itself pointed users to this package when it dropped the built-in component), not an obscure or unvetted third-party choice. Callstack is a known, established React Native consultancy that maintains several widely-used community RN modules.
- **Maintenance**: latest npm version (5.2.0) is exactly what's pinned - not behind. Published 2026-04-03. 76 versions published since first release in 2019 - long-lived, actively released package, not abandoned or newly-created.
- **Transitive dependencies**: zero runtime dependencies (`dependencies: null` in `package.json`) - the entire risk surface is the package's own code plus its native (Obj-C/Swift/Java/C++) sources, not a dependency chain.
- **Native surface (the part that matters most for a non-Expo-managed module)**:
  - Android: `AndroidManifest.xml` contributed by the library declares no `<uses-permission>` entries - a slider has no legitimate reason to need any, and it doesn't request any.
  - iOS: podspec pulls in standard React Native new-architecture build dependencies (`React-Core`, `React-RCTFabric`, `React-Codegen`, `RCT-Folly`, `ReactCommon/turbomodule/core`) - all first-party React Native build infrastructure, not third-party native SDKs. No `Info.plist` usage-description keys required (no camera/location/contacts/etc. entitlements requested).
  - No native build script (`podspec`/`build.gradle`) runs anything beyond standard CocoaPods/Gradle compilation - no `system()`/`exec` calls, no download-and-run-at-build-time patterns.
- **Install lifecycle scripts**: package's own `package.json` scripts are `prepare`/`lint`/`test`/`prepack` only (build-from-source steps that ran when the package itself was published, not scripts that execute in this project's install) - no `preinstall`/`install`/`postinstall` hook that runs code in this project's `npm install`.
- **Known CVEs**: none found for `@react-native-community/slider@5.2.0` (npm audit clean, OSV.dev query returned no advisories at any version).

**Assessment**: clean. As a non-Expo-managed native module it carries inherently more surface area than the project's usual Expo-managed dependencies (its own native build config, no Expo-team release cadence backing it), but nothing here — provenance, permissions, maintenance cadence, or dependency count — sets off any of the usual community-package red flags (no permission over-reach, no lifecycle-script code execution, no abandoned-package staleness, no unvetted/typosquat-risk provenance). Worth a routine re-check on future version bumps given it's the project's first non-Expo-managed native module, but nothing here blocks this phase.
